# Теория аудио

Личный учебник по теории аудио и цифровой обработке звука: самостоятельные статьи, визуализации и интерактивные примеры. Материалы пишутся на русском с английскими названиями основных терминов. Статический сайт опубликован на [GitHub Pages](https://hazadus.github.io/audio-theory/).

## Разработка

Нужны Node.js 22 (≥ 22.13.0), 24 или ≥ 26, npm ≥ 9.6.5 и [just](https://just.systems/). Зависимости зафиксированы в `package.json` и `package-lock.json`; установка из чистого checkout:

```sh
npm ci
```

Запуск из корня проекта:

```sh
just dev
```

Возьмите адрес из вывода Astro: строка `Local` в обычном терминале или сообщение `Dev server running at` при фоновом запуске. Фоновое сообщение может содержать только origin; добавьте фактический базовый путь `/audio-theory/` ровно один раз (обычно сайт открывается по `http://localhost:4321/audio-theory/`). При занятом порте Astro выбирает другой. Для проверки на определённом интерфейсе и порте:

```sh
just dev --host 127.0.0.1 --port 4321
```

В обычном терминале сервер работает до `Ctrl-C`. Astro 7 автоматически запускает сервер агента в фоне и завершает команду; для управления из корня проекта доступны:

```sh
npm run dev -- status
npm run dev -- logs
npm run dev -- stop
```

Агент сохраняет PID и URL своего сервера (либо ID активной сессии или фоновой задачи). Перед остановкой фонового сервера он сверяет PID и URL через `status` и останавливает только собственный процесс; на время авторской проверки сервер остаётся доступным. Чужой сервер не останавливается и не заменяется через `--force`.

Сборка:

```sh
just build
```

Результат находится в `dist/`: HTML, ресурсы и индекс Pagefind для статического хостинга. Сборка проверяет внутренние страницы, HTML-якоря и ресурсы HTML/CSS; неверная цель останавливает её. Конфигурация Astro явно использует `output: 'static'`. TypeScript использует конфигурацию `astro/tsconfigs/strict`; `just` показывает доступные команды с русскими пояснениями.

Новые открытые вопросы записывайте в `docs/questions.md`, согласованные требования — в `docs/spec.md`. Статьи проверяются автором на локальном сайте и публикуются только после одобрения.

Импорты файлов из `src/` в коде приложения и Astro/MDX-компонентах используют алиас `@/`, заданный в `tsconfig.json`, например `@/styles/math.css`. Astro применяет его при разработке и сборке. Правила импортов описаны в [стайлгайде](./docs/styleguide.md#конфигурация).

## Проверки кода и браузерные тесты

```sh
just fmt                 # Prettier: форматирование исходников и конфигурации
npm run fmt:check        # Проверка форматирования без записи
just lint                # ESLint: JavaScript, TypeScript и Astro
just typecheck           # Astro Check и tsc --noEmit
just test                # Vitest: unit-тесты
just build               # Статическая сборка
just test-e2e            # Обязательный сокращённый набор, как в CI
just test-e2e-full       # Полная матрица Playwright для диагностики
just test-production https://hazadus.github.io/audio-theory/ # Проверка опубликованного сайта
```

Prettier форматирует `.astro`, CSS, JavaScript, TypeScript и JSON; документация, HTML-макеты, MDX и генерируемые файлы исключены. ESLint проверяет код, включая служебные Astro-компоненты, но не демонстрационный рантайм макетов. Unit-тесты находятся в `tests/unit/`, браузерные сценарии — в `tests/e2e/`; Vitest не запускает сценарии Playwright. TypeScript закреплён на версии 6.0.3, совместимой с Astro Check и typescript-eslint.

Перед первым браузерным прогоном установите браузеры:

```sh
npx playwright install chromium firefox webkit
```

В Linux CI используйте `npx playwright install --with-deps chromium firefox webkit`. `just test-e2e` проверяет обе сборки сокращённым набором, используемым также в CI, а сценарии эксперимента дискретизации и заметок «Подробнее» — на отдельной служебной сборке; `just test-e2e-full` запускает полную матрицу для диагностики. Распределение сценариев между браузерами и базовыми путями описано в [обзоре](docs/overview.md#браузерные-проверки). Начальные сценарии проверяют текст, навигацию, стили, локальный ресурс и отсутствие служебного маршрута, чтение без JavaScript на ширине 390 px и поиск по настоящему индексу Pagefind через API.

Playwright запускает собственные preview-серверы на `127.0.0.1:4391`, `127.0.0.1:4392` и `127.0.0.1:4393` и останавливает их после прогона. `--ignore-lock` оставляет процессы в foreground без общего lock-файла Astro; занятый порт вызывает ошибку, чужой сервер не используется. Локальный dev-сервер для авторской проверки работает независимо. Результаты и trace при ошибках сохраняются в `test-results/`; эти файлы и `.e2e/` не входят в Git.

DOM можно исследовать через `page.locator()`, `page.getByRole()` и `page.evaluate()`, снимок сделать через `page.screenshot()`. Trace открывается командой `npx playwright show-trace <путь-к-trace.zip>`. При изменении критичного пользовательского пути, доступности элементов или обработки адресов нужен весь обязательный набор `just test-e2e`; отдельный файл его не заменяет. WebKit не заменяет ручную проверку настоящего Safari на Mac и iPhone. Команда `just screenshots` появится вместе с соответствующей задачей.

Параметры smoke-проверки опубликованного сайта описаны в [инструкции по деплою](./docs/deploy.md#проверка-опубликованного-сайта).

## Скиллы агентов

| Задача | Codex | Claude Code |
| --- | --- | --- |
| Подготовить или дополнить материал по теме и уточнениям | `$write-article <тема>; <уточнения>` | `/write-article <тема>; <уточнения>` |
| Проверить изменения и создать логические коммиты | `$commit` | `/commit` |
| Выполнить указанный пункт `docs/todos.md`, проверить и закоммитить | `$execute 4` | `/execute 4` |
| Выполнить GitHub issue, дать результат на проверку и отчитаться в issue | `$issue 26` | `/issue 26` |

Скиллы учитывают наличие команд и тестов на текущем этапе разработки. Материалы включаются в коммит только после личной проверки и одобрения автором; обычные локальные задачи не запускают пуш. При порученной публикации проверяются CI, деплой и опубликованный сайт. Скиллы обоих агентов используют [общие правила](./docs/authoring/rules.md) и [чеклист](./docs/authoring/checklist.md). `execute` и `issue` вызывают `write-article` при подготовке материалов, передавая тему, согласованный уровень и ограничения пользователя; завершение задачи остаётся в вызывающем процессе.

`write-article` доступен при работе из этого репозитория: [Codex](./.agents/skills/write-article/SKILL.md) и [Claude Code](./.claude/skills/write-article/SKILL.md). При новых математических инструментах скилл также дополняет статью [«Математика для аудио»](./src/content/articles/audio-math.mdx); готовое объяснение связывает с новым материалом ссылкой на раздел. Тема обязательна; уровень и другие уточнения можно передать обычным текстом, без фиксированного синтаксиса параметров. Например, в сообщении Codex:

```text
$write-article дискретизация; для начинающего; объясни период на числовом примере
```

В Claude Code:

```text
/write-article дискретизация; для начинающего; объясни период на числовом примере
```

Скилл сначала читает существующие материалы и выбирает дополнение или новую статью. Если понятие уже раскрыто, он исправляет или дополняет конкретный пробел, сохраняя существующие якоря. По умолчанию объяснение начинается с основ. В Codex, если новая точка входа ещё не появилась в текущем списке скиллов, начать новую сессию из корня проекта; при вызове из `execute`/`issue` инструкция также содержит прямую ссылку на её файл.

Самостоятельный `write-article` готовит материал, выполняет применимые проверки и передаёт автору локальные URL и результаты чеклиста в ответе, без отдельных документов с отчётом о проверках. Он не создаёт коммит, не отмечает задачу и не публикует сайт. Автор читает материал на локальном сайте, после доработок явно одобряет текущий текст. Затем можно вызвать `commit` или продолжить начатый `execute`/`issue`; публикация выполняется только по отдельному поручению или прямому требованию задачи. Ограничение «не коммитить до моей проверки» действует и при вложенном вызове.
