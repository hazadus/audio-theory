# Коммит изменений

Закоммитить текущие staged, unstaged и untracked изменения по [стайлгайду](../../../docs/styleguide.md) с учётом [правил проверки и публикации](../../../docs/spec.md#проверка-и-публикация).

## Шаги

1. **Осмотреть изменения**
   - Проверить `git status`, `git diff`, `git diff --staged` и содержимое новых файлов. Выяснить, какие изменения связаны между собой и какие проверки для них нужны.

2. **Проверить затронутое**
   - Сборка сайта уже доступна: `just build` вызывает `npm run build` и создаёт статические файлы в `dist/`. Выполнять её при изменениях приложения или конфигурации сборки.
   - `just build` также строит `dist/pagefind/` и проверяет локальные ссылки, HTML-якоря и ресурсы HTML/CSS без сетевой проверки внешних адресов; ошибка останавливает сборку. Фактические `base` и `outDir` учитываются при переопределении из CLI. Поиск по настоящему индексу проверяется полным `just test-e2e`; dev-сервер индекс не строит. Ручная проверка API на собранном сайте описана в [обзоре](../../../docs/overview.md#поисковый-индекс-и-проверка-артефакта). Проверки содержимого статей входят в `just build` и `astro build`: схема frontmatter, уникальность `slug`, якоря, Git-дата, источники, внутренние ссылки, язык листингов, идентификаторы и нумерация блоков (`assertValidArticles`), затем ссылки, якоря и ресурсы готового HTML. Отдельной команды для них нет; контрольные ошибки и изоляцию служебных статей проверяет `npm run test:articles`, он же выполняется в CI до `test:e2e`.
   - При изменении схемы, загрузки или целей треков выполнить `npm run test:tracks`: корректные служебные маршруты собираются в корне и под префиксом, неизвестная статья/раздел, повторный id элемента и пустой этап останавливают сборку; последующие обычные сборки подтверждают изоляцию фикстур от HTML, RSS, клиентских ресурсов и Pagefind. Служебные данные — `tests/fixtures/tracks/`, переменная `TRACKS_DIR` описана в `.env.example`; публичная сборка её не задаёт. Проверка также подтверждает обязательную запись «Новое» для публичного трека и «Черновик» без журнала в локальном режиме. При изменении журнала треков выполнить `npm run test:track-updates`: служебные сборки и Chromium/WebKit проверяют журнал, архив, фильтры, RSS, последние обновления, даты и ссылки этапов под обоими базовыми путями, в обеих темах и без JS. Эти фикстуры не публикуются. Команды сборки и `just typecheck` выполнять последовательно из-за общего кеша Astro.
   - При изменении обработки MDX, формул или их ресурсов выполнить `npm run test:mdx`: проверка собирает служебные материалы из `tests/fixtures/mdx/`, подтверждает MathML и локальные ресурсы, ошибку неверной формулы и отсутствие тестовых страниц в публичной сборке. Просмотр тестовой страницы описан в [обзоре](../../../docs/overview.md#проверка-mdx-и-формул).
   - При изменении схемы статей, групп или маршрутов выполнить `npm run test:articles`: проверка собирает служебные статьи из `tests/fixtures/articles/`, подтверждает маршрут из `slug`, отказ при повторном `slug`, неизвестной группе, пустых полях и неверном `readingMinutes`, отсутствие служебных статей в публичной сборке, «Черновик» для файла без коммита и ошибку публикуемой сборки без Git-даты, якоря `{#anchor}`, оглавление H2/H3 и ссылки на разделы под префиксом; повторный, неверный и неуместный якорь блокируют сборку; отсутствие источников, неверные ссылки и связанные темы, блок кода без языка, неверные идентификаторы и нумерация рисунков, таблиц и формул блокируют сборку, а превышение рекомендательных лимитов нет; в индекс Pagefind служебные статьи не попадают.
   - Для кода использовать существующие рецепты корневого `justfile`: `just fmt`, `just lint`, `just typecheck`, `just test`, `just build` по характеру изменений. После форматирования проверить `npm run fmt:check`; пропущенную проверку не выдавать за успешную.
   - При изменении критичного пользовательского пути, доступности элементов или обработки адресов выполнить полный `just test-e2e`; отдельный файл не заменяет полный прогон. При изменении поведения сначала обновить относящиеся к нему тесты. Для интерфейса выполнить требуемую задачей браузерную или визуальную проверку.
   - Документация и инструкции без изменения кода не требуют сборки и тестов приложения. Проверить ссылки, актуальность описанного поведения и согласованность со [спецификацией](../../../docs/spec.md). Статьи MDX и определения глоссария требуют проверки контента и сборки.
   - При работе с материалами до подготовки или проверки прочитать [общие правила](../../../docs/authoring/rules.md) и [чеклист](../../../docs/authoring/checklist.md), применять их к текущим правкам и записать результаты до передачи автору. Пути разрешаются относительно этого `SKILL.md` в обоих агентах; правила не копировать в скилл.
   - Для новой статьи или существенного дополнения опубликованной статьи убедиться, что есть запись журнала `src/content/updates/<id>.json` по [правилам журнала](../../../docs/authoring/rules.md#журнал-обновлений) и [шаблону](../../../docs/authoring/update-template.md); для исправления опечатки запись не требуется. Сборка останавливается на неверной цели ссылки пункта.
   - Если в изменениях есть файлы `src/content/tracks/`, убедиться по [правилам о треках](../../../docs/authoring/rules.md#треки-чтения), что состав и запись журнала с целью `track` показаны автору и одобрены, и входят в один коммит с материалом; опечатка и правка статьи без изменения маршрута записи о треке не требуют. При изменении схемы или целей выполнить `npm run test:tracks`.
   - Новую статью до коммита собирать так: `ALLOW_DRAFT_ARTICLES=1 just build` — страница показывает «Черновик» вместо даты (`just dev` включает этот режим сам). Обычный `just build` и CI без переменной требуют настоящей Git-даты коммита файла и полной истории: файл без коммита или неполный клон останавливают сборку. Переменную не задавать в CI и при публикации, требования к Git-датам не обходить. Проверить метаданные, внутренние ссылки и якоря.
   - При падении применимой проверки исправить причину и повторить её. Если обязательная проверка невозможна, сообщить о препятствии и не коммитить непроверенную работу.

3. **Подготовить коммиты**
   - Статьи, изменения их текста, определения глоссария и текст «О проекте» включать вместе с записью журнала обновлений только после локальной проверки и явного одобрения автором; запись входит в тот же коммит, что и материал. Вызов скилла не заменяет авторскую проверку; уже полученное одобрение текущих правок действует. Неодобренные материалы оставить вне коммита; независимые проверенные изменения можно закоммитить.
   - Разделить несвязанные правки на отдельные логические коммиты. Проверить, что новая переменная окружения описана в `.env.example`, а связанные документы и `README.md` обновлены, если этого требуют правила проекта.
   - Сообщение составить по разделу «Git: сообщения коммитов» [стайлгайда](../../../docs/styleguide.md): русский текст, разрешённый тип, необязательный `scope`, тема не длиннее 72 символов, без точки и трейлеров об инструментах.
   - Добавлять конкретные пути через `git add <путь>`. Не включать секреты, локальные `.env`, зависимости, тестовые данные и артефакты сборки.

4. **Закоммитить и проверить**
   - Создать новый коммит без `--no-verify` и без изменения предыдущего коммита. Проверить состав и сообщение через `git log -1 --stat`, затем состояние рабочего дерева.

Не пушить без явной просьбы пользователя или требования выбранной задачи. Этот скилл создаёт локальный коммит; порученную публикацию выполнять отдельным процессом по [инструкции по CI и деплою](../../../docs/deploy.md).

Использование: `/commit`

## Адреса при локальной проверке

Конфигурация `src/site.config.ts` задаёт стандартный базовый путь `/audio-theory/`. Фоновый Astro может сообщать только origin без префикса: открывать сайт по origin и фактическому `base`, добавляя его ровно один раз. Для проверки корневого размещения использовать параметр `--base /` при запуске и сборке (`npm run build -- --base /`). Служебный маршрут MDX — `<origin><base>__test/mdx/`. Построитель `withBase` и обычные MDX-ссылки используют фактический базовый путь, включая переопределение из CLI.

## Браузерные проверки и DOM

`just test-e2e` последовательно собирает сайт в `.e2e/root/` и `.e2e/prefixed/`, затем запускает обязательный набор Playwright: не более 12 сценариев `@ci` — 11 в WebKit под префиксом и один (`@ci-root`) в Chromium в корне. Жёсткое правило: метку `@ci` новым сценариям не добавлять и лимит не повышать; новый сценарий CI заменяет существующий, остальные идут только в `just test-e2e-full`. `node scripts/check-e2e-budget.mjs` проверяет лимит 12. Именно этот набор выполняется в CI; он является полным обязательным прогоном при изменении критичного пути. `just test-e2e-full` запускает прежнюю матрицу всех сценариев в трёх браузерах под обоими базовыми путями для диагностики. Правила выбора сценариев описаны в [обзоре](../../../docs/overview.md#браузерные-проверки). Перед первым запуском установить браузеры: `npx playwright install chromium firefox webkit` (для Linux CI — `npx playwright install --with-deps chromium firefox webkit`). Playwright управляет своими preview-серверами на 4391 и 4392; `--ignore-lock` оставляет их в foreground без общего lock-файла Astro, а `reuseExistingServer: false` запрещает использовать чужой сервер. Занятый порт означает ошибку проверки.

Сценарии DOM находятся в `tests/e2e/`, unit-тесты — в `tests/unit/`. Для исследования DOM доступны `page.locator()`, `page.getByRole()` и `page.evaluate()`; для снимка — `page.screenshot()`. Снимки и trace смотреть локальными средствами агента; WebKit не заменяет ручную проверку Safari. `just test-production https://hazadus.github.io/audio-theory/` проверяет опубликованную начальную страницу и ресурсы; передавать фактический публичный URL с базовым путём. Параметры описаны в [инструкции по деплою](../../../docs/deploy.md#проверка-опубликованного-сайта). Команда не публикует сайт; при отдельно порученной публикации запускать после успешного деплоя нужного SHA.
