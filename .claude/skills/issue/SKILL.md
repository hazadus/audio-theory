# Работа по issue

Довести GitHub issue с номером из `$ARGUMENTS` до проверенного и задокументированного результата. Плановая разработка ведётся по [плану](../../../docs/plan.md) и [задачам](../../../docs/todos.md) через `/execute`; issue не дублирует их пункты.

## Шаги

1. **Прочитать issue и правила**
   - Получить заголовок, тело, метки, комментарии и URL командой `gh issue view <номер> --json number,title,body,labels,comments,url`. Для сетевых команд `gh` использовать разрешённый окружением доступ; если изолированный `Bash` не имеет сети, запросить запуск с `dangerouslyDisableSandbox: true`.
   - Если приложен скриншот, скачать его через авторизованный `gh api -H 'Accept: application/octet-stream' '<url>'` во временный файл, проверить формат командой `file` и открыть через `Read` с поддержкой изображений. Для вложения приватного репозитория обычный `curl` может вернуть `Not Found`.
   - Учесть все просьбы и ограничения из текста и комментариев. Свериться с [правилами репозитория](../../../CLAUDE.md), [планом](../../../docs/plan.md), [задачами](../../../docs/todos.md), [спецификацией](../../../docs/spec.md), [дизайн-системой](../../../docs/design-system.md) и [открытыми вопросами](../../../docs/questions.md), когда они относятся к issue.
   - Если issue повторяет плановый пункт, указать на существующую задачу и согласовать границу работы до реализации; не переносить содержание issue в `docs/todos.md`.

2. **Разобраться в реализации и обсудить результат**
   - Найти затронутые модули, компоненты, тесты и текущее поведение. Использовать существующие механизмы, если они решают задачу.
   - До правки сообщить пользователю понимание проблемы, предлагаемое поведение, существенные решения и затрагиваемые файлы. Вопросы по неразрешённым продуктовым развилкам задать через `AskUserQuestion`; способ реализации выбрать самостоятельно. Дождаться ответа на обязательные вопросы до изменения поведения.

3. **Реализовать и проверить**
   - Следовать [структуре проекта](../../../docs/structure.md), [стайлгайду](../../../docs/styleguide.md) и [дизайн-системе](../../../docs/design-system.md). «Теория аудио» — статический сайт Astro с MDX, KaTeX, Shiki и Pagefind на GitHub Pages. Основной HTML создаётся при сборке, интерактивные элементы работают в браузере; ссылки и ресурсы учитывают базовый путь размещения. Учитывать статусы инструментов в [техническом стеке](../../../docs/techstack.md).
   - Обновить существующие проверки изменённого контракта и добавить осмысленные unit-тесты для предметной логики; поведение DOM проверять компонентным тестом. Полный `just test-e2e` нужен при изменении критичного пользовательского пути или доступности элементов. E2E проверяют браузерные сценарии на собранном сайте с реальным индексом Pagefind, включая размещение под префиксом; варианты чистой логики проверять unit-тестами.
   - Для материалов изучить существующие статьи и [темы](../../../docs/topics.md), избегать дублирования и соблюдать контракты метаданных, ссылок и учебных компонентов из спецификации. Материалы — на русском с английским названием основного термина при первом упоминании. Проверить источники, термины, формулы и расчёты; выполнить редакционную проверку по tropes.md до передачи автору. Использовать общий набор правил `docs/authoring/` и скилл `/write-article`, когда они созданы; до этого руководствоваться спецификацией.
   - Новые статьи до коммита собирать в локальном режиме с состоянием «Черновик»; опубликованная сборка требует настоящей Git-даты. Проверить метаданные, внутренние ссылки и якоря; требования к Git-датам в CI не обходить.
   - Выполнить применимые `just fmt`, `just lint`, `just typecheck`, `just test`, `just build`; при изменении критичного пути или доступности элементов — полный `just test-e2e`. При изменении интерфейса проверить нужные размеры и состояния в браузере, а при затрагивании визуальных эталонов — `just screenshots` с просмотром снимков. Исправить причины ошибок и повторить соответствующие проверки.
   - Пока приложение, `justfile` или отдельные проверки ещё не созданы, выполнить доступные прямые команды и проверки затронутых документов; отсутствие команды не выдавать за успешную проверку. Если обязательная для issue проверка недоступна, назвать препятствие и не коммитить непроверенную работу.
   - Для визуализаций и аудио проверить численные и граничные случаи, согласованность графика и звука, запуск действием пользователя и остановку при уходе со страницы. Необходимую ручную проверку в настоящем Safari на Mac и iPhone не заменять WebKit-тестами.
   - Новые открытые вопросы записывать в [questions.md](../../../docs/questions.md), согласованные требования — в спецификацию.
   - Записать новое наблюдаемое поведение в профильный документ, обычно [спецификацию](../../../docs/spec.md); обновить [дизайн-систему](../../../docs/design-system.md) при изменении внешнего вида и `README.md` при изменении статуса, команд или состава документов.

4. **Дать пользователю проверить результат**
   - Для сайта запустить `just dev` и оставить его доступным на время проверки. Сообщить адрес, изменения и конкретный сценарий для просмотра; попросить замечания или явное подтверждение, что их нет. Для задачи только с документацией или инструкциями без приложения дать ссылки на изменённые файлы и конкретный результат для проверки.
   - Статьи, изменения их текста, определения глоссария и текст «О проекте» требуют личной авторской проверки на локальном сайте до коммита. Вызов скилла не заменяет одобрение; уже полученное одобрение текущих правок действует.
   - Дождаться ответа. При замечаниях исправить их, повторить нужные проверки и вновь передать результат на просмотр. Отсутствие ответа не считать одобрением. После подтверждения остановить процессы, запущенные для проверки.

5. **Завершить issue после подтверждения**
   - Закоммитить по [`/commit`](../commit/SKILL.md): один логический коммит на issue, без `--no-verify` и без пуша. В теле сообщения добавить простую ссылку `#<номер>` без `Closes` и `Fixes`; issue остаётся открытым для решения пользователя. Если пользователь просит пока не коммитить, оставить проверенные изменения без коммита до отдельного разрешения.
   - Оставить комментарий командой `gh issue comment <номер> -F -` по форме ниже. Сообщить пользователю SHA, ссылку на комментарий, результат и проверки.

   ```text
   Коммит: <полный SHA>
   Исполнитель: Claude Code / <модель>

   <что и почему изменено; какие проверки прошли; где обновлена документация>
   ```

## После ревью

Если после завершения пользователь сообщает о регрессии или недоделке, исправить её, снова выполнить применимые проверки и локальную проверку пользователем, затем создать отдельный коммит и комментарий той же формы. `--amend` использовать только по явной просьбе. Issue не закрывать самостоятельно и не пушить без явной просьбы. При порученной публикации после одобрения материалов пушить в основную ветку без обязательного PR, проверить CI и деплой GitHub Pages, затем выполнить доступный `just test-production`; неодобренные материалы исключить из публикуемого коммита.

Использование: `/issue 26`
