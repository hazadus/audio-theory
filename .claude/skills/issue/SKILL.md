# Работа по issue

Довести GitHub issue с номером из `$ARGUMENTS` до проверенного и задокументированного результата. Плановая разработка ведётся по [плану](../../../docs/plan.md) и [задачам](../../../docs/todos.md) через `/execute`; issue не дублирует их пункты.

## Шаги

1. **Прочитать issue и правила**
   - Получить заголовок, тело, метки, комментарии и URL командой `gh issue view <номер> --json number,title,body,labels,comments,url`. Для сетевых команд `gh` использовать разрешённый окружением доступ; если изолированный `Bash` не имеет сети, запросить запуск с `dangerouslyDisableSandbox: true`.
   - Если приложен скриншот, скачать его через авторизованный `gh api -H 'Accept: application/octet-stream' '<url>'` во временный файл, проверить формат командой `file` и открыть через `Read` с поддержкой изображений. Для вложения приватного репозитория обычный `curl` может вернуть `Not Found`.
   - Учесть все просьбы и ограничения из текста и комментариев. Свериться с [правилами репозитория](../../../CLAUDE.md), [планом](../../../docs/plan.md), [задачами](../../../docs/todos.md), [спецификацией](../../../docs/spec.md), [дизайн-системой](../../../docs/design-system.md) и [открытыми вопросами](../../../docs/questions.md), когда они относятся к issue.
   - Если issue повторяет плановый пункт, указать на существующую задачу и согласовать границу работы до реализации; не переносить содержание issue в `docs/todos.md`.

2. **Разобраться в реализации и обсудить результат**
   - Найти затронутые модули, компоненты, тесты и текущее поведение. Использовать существующие механизмы, если они решают задачу.
   - До правки сообщить пользователю понимание проблемы, предлагаемое поведение, существенные решения и затрагиваемые файлы. Вопросы по неразрешённым продуктовым развилкам задать через `AskUserQuestion`; способ реализации выбрать самостоятельно. Дождаться ответа на обязательные вопросы до изменения поведения.

3. **Реализовать и проверить**
   - Следовать [структуре проекта](../../../docs/structure.md), [стайлгайду](../../../docs/styleguide.md) и [дизайн-системе](../../../docs/design-system.md). «Теория аудио» — статический сайт Astro с MDX, KaTeX, Shiki и Pagefind на GitHub Pages. Основной HTML создаётся при сборке, интерактивные элементы работают в браузере; ссылки и ресурсы учитывают базовый путь размещения. Учитывать статусы инструментов в [техническом стеке](../../../docs/techstack.md).
   - Обновить существующие проверки изменённого контракта и добавить осмысленные unit-тесты для предметной логики; поведение DOM проверять в Playwright через локаторы и `expect`, доступность — через роли и доступные имена. Полный `just test-e2e` нужен при изменении критичного пользовательского пути, доступности элементов или обработки адресов; отдельный файл не заменяет полный прогон. E2E проверяют собранный сайт в корне и под префиксом; после подключения Pagefind поисковые сценарии используют настоящий индекс; варианты чистой логики проверять unit-тестами.
   - Для создания или дополнения материалов вызвать `/write-article` через инструмент `Skill` с именем `write-article` и аргументами темы/уточнений. Передать тему из задачи, согласованный уровень объяснения и все ограничения пользователя, включая запрет коммита или публикации. Скилл читает [общие правила](../../../docs/authoring/rules.md) и [чеклист](../../../docs/authoring/checklist.md), готовит материал и возвращает файлы, локальные URL и результаты проверок. Затем продолжить этот процесс: выполнить критерий задачи и авторскую приёмку; коммит, отметка выполнения и публикация остаются его ответственностью и ждут предусмотренного одобрения. Для проверки уже подготовленных материалов прочитать общие правила и чеклист напрямую; повторно запускать подготовку без необходимости не нужно.
   - Новую статью до коммита собирать так: `ALLOW_DRAFT_ARTICLES=1 just build` — страница показывает «Черновик» вместо даты (`just dev` включает этот режим сам). Обычный `just build` и CI без переменной требуют настоящей Git-даты коммита файла и полной истории: файл без коммита или неполный клон останавливают сборку. Переменную не задавать в CI и при публикации, требования к Git-датам не обходить. Проверить метаданные, внутренние ссылки и якоря.
   - Выполнить применимые `just fmt`, `just lint`, `just typecheck`, `just test`, `just build`; при изменении критичного пути, доступности элементов или обработки адресов — полный `just test-e2e`. При изменении интерфейса проверить нужные размеры и состояния в браузере, а при затрагивании визуальных эталонов — снимки через `page.screenshot()` в Playwright с просмотром результата; общий рецепт `just screenshots` добавляется в задаче 54. Исправить причины ошибок и повторить соответствующие проверки.
   - Доступная сборка сайта: `just build` (вызывает `npm run build`, результат — `dist/`).
   - `just build` также строит `dist/pagefind/` и проверяет локальные ссылки, HTML-якоря и ресурсы HTML/CSS без сетевой проверки внешних адресов; ошибка останавливает сборку. Фактические `base` и `outDir` учитываются при переопределении из CLI. Поиск по настоящему индексу проверяется полным `just test-e2e`; dev-сервер индекс не строит. Ручная проверка API на собранном сайте описана в [обзоре](../../../docs/overview.md#поисковый-индекс-и-проверка-артефакта). Проверки содержимого статей входят в `just build` и `astro build`: схема frontmatter, уникальность `slug`, якоря, Git-дата, источники, внутренние ссылки, язык листингов, идентификаторы и нумерация блоков (`assertValidArticles`), затем ссылки, якоря и ресурсы готового HTML. Отдельной команды для них нет; контрольные ошибки и изоляцию служебных статей проверяет `npm run test:articles`, он же выполняется в CI до `test:e2e`.
   - При изменении обработки MDX, формул или их ресурсов выполнить `npm run test:mdx`: проверка собирает служебные материалы из `tests/fixtures/mdx/`, подтверждает MathML и локальные ресурсы, ошибку неверной формулы и отсутствие тестовых страниц в публичной сборке. Просмотр тестовой страницы описан в [обзоре](../../../docs/overview.md#проверка-mdx-и-формул).
   - При изменении схемы статей, групп или маршрутов выполнить `npm run test:articles`: проверка собирает служебные статьи из `tests/fixtures/articles/`, подтверждает маршрут из `slug`, отказ при повторном `slug`, неизвестной группе, пустых полях и неверном `readingMinutes`, отсутствие служебных статей в публичной сборке, «Черновик» для файла без коммита и ошибку публикуемой сборки без Git-даты, якоря `{#anchor}`, оглавление H2/H3 и ссылки на разделы под префиксом; повторный, неверный и неуместный якорь блокируют сборку; отсутствие источников, неверные ссылки и связанные темы, блок кода без языка, неверные идентификаторы и нумерация рисунков, таблиц и формул блокируют сборку, а превышение рекомендательных лимитов нет; в индекс Pagefind служебные статьи не попадают.
   - Проверить форматирование через `npm run fmt:check`. Пропущенную проверку не выдавать за успешную. Если обязательная для issue проверка недоступна, назвать препятствие и не коммитить непроверенную работу.
   - Для визуализаций и аудио проверить численные и граничные случаи, согласованность графика и звука, запуск действием пользователя и остановку при уходе со страницы. Необходимую ручную проверку в настоящем Safari на Mac и iPhone не заменять WebKit-тестами.
   - Новые открытые вопросы записывать в [questions.md](../../../docs/questions.md), согласованные требования — в спецификацию.
   - Записать новое наблюдаемое поведение в профильный документ, обычно [спецификацию](../../../docs/spec.md); обновить [дизайн-систему](../../../docs/design-system.md) при изменении внешнего вида и `README.md` при изменении статуса, команд или состава документов.

4. **Дать пользователю проверить результат**
   - Для локальной проверки запускать из корня `just dev --host 127.0.0.1 --port 4321`. Фактический URL брать из вывода Astro: строка `Local` в обычном терминале или сообщение `Dev server running at` при фоновом запуске. Занятый порт может изменить адрес. В Claude Code запускать через `Bash` с `run_in_background: true`, сохранить ID задачи; читать вывод через `TaskOutput`. Если процесс остался в задаче, остановить его через `TaskStop` по этому ID и проверить завершение. Astro 7 автоматически запускает сервер агента в фоне и завершает команду: тогда сохранить PID и URL из вывода, проверить их через `npm run dev -- status`, читать логи через `npm run dev -- logs`. Перед остановкой снова сверить PID и URL через `status` с сохранёнными и только при совпадении выполнить из того же корня `npm run dev -- stop`, затем проверить `status`. Совместимый уже запущенный сайт можно использовать повторно; чужие процессы не останавливать и не заменять через `--force`. После своей проверки останавливать только собственный процесс; на время ожидаемой авторской проверки оставить его доступным. Не использовать массовые `pkill` или `killall`.
   - Сообщить фактический URL, изменения и конкретный сценарий для просмотра; попросить замечания или явное подтверждение, что их нет. Для задачи только с документацией или инструкциями без приложения дать ссылки на изменённые файлы и конкретный результат для проверки.
   - Статьи, изменения их текста, определения глоссария и текст «О проекте» требуют личной авторской проверки на локальном сайте до коммита. Вызов скилла не заменяет одобрение; уже полученное одобрение текущих правок действует.
   - Дождаться ответа. При замечаниях исправить их, повторить нужные проверки и вновь передать результат на просмотр. Отсутствие ответа не считать одобрением. После подтверждения остановить только собственные процессы, запущенные для этой проверки, по сохранённому ID.

5. **Завершить issue после подтверждения**
   - Закоммитить по [`/commit`](../commit/SKILL.md): один логический коммит на issue, без `--no-verify` и без пуша. В теле сообщения добавить простую ссылку `#<номер>` без `Closes` и `Fixes`; issue остаётся открытым для решения пользователя. Если пользователь просит пока не коммитить, оставить проверенные изменения без коммита до отдельного разрешения.
   - Оставить комментарий командой `gh issue comment <номер> -F -` по форме ниже. Сообщить пользователю SHA, ссылку на комментарий, результат и проверки.

   ```text
   Коммит: <полный SHA>
   Исполнитель: Claude Code / <модель>

   <что и почему изменено; какие проверки прошли; где обновлена документация>
   ```

## После ревью

Если после завершения пользователь сообщает о регрессии или недоделке, исправить её, снова выполнить применимые проверки и локальную проверку пользователем, затем создать отдельный коммит и комментарий той же формы. `--amend` использовать только по явной просьбе. Issue не закрывать самостоятельно и не пушить без явной просьбы. При порученной публикации следовать [инструкции по CI и деплою](../../../docs/deploy.md), включая порядок коммита и пуша, авторское одобрение материалов и проверку деплоя нужного SHA.

## Адреса при локальной проверке

Конфигурация `src/site.config.ts` задаёт стандартный базовый путь `/audio-theory/`. Фоновый Astro может сообщать только origin без префикса: открывать сайт по origin и фактическому `base`, добавляя его ровно один раз. Для проверки корневого размещения использовать параметр `--base /` при запуске и сборке (`npm run build -- --base /`). Служебный маршрут MDX — `<origin><base>__test/mdx/`. Построитель `withBase` и обычные MDX-ссылки используют фактический базовый путь, включая переопределение из CLI.

## Браузерные проверки и DOM

`just test-e2e` последовательно собирает сайт в `.e2e/root/` и `.e2e/prefixed/`, затем запускает обязательный сокращённый набор Playwright: все сценарии в WebKit под префиксом, сценарии `@cross-browser` в Chromium и Firefox под префиксом, сценарии `@placement` в Chromium в корне. Именно этот набор выполняется в CI; он является полным обязательным прогоном при изменении критичного пути. `just test-e2e-full` запускает прежнюю матрицу всех сценариев в трёх браузерах под обоими базовыми путями для диагностики. Правила выбора сценариев описаны в [обзоре](../../../docs/overview.md#браузерные-проверки). Перед первым запуском установить браузеры: `npx playwright install chromium firefox webkit` (для Linux CI — `npx playwright install --with-deps chromium firefox webkit`). Playwright управляет своими preview-серверами на 4391 и 4392; `--ignore-lock` оставляет их в foreground без общего lock-файла Astro, а `reuseExistingServer: false` запрещает использовать чужой сервер. Занятый порт означает ошибку проверки.

Сценарии DOM находятся в `tests/e2e/`, unit-тесты — в `tests/unit/`. Для исследования DOM доступны `page.locator()`, `page.getByRole()` и `page.evaluate()`; для снимка — `page.screenshot()`. Снимки и trace смотреть локальными средствами агента; WebKit не заменяет ручную проверку Safari. При порученной публикации после успешного деплоя нужного SHA выполнить `just test-production https://hazadus.github.io/audio-theory/`: передать фактический публичный URL окружения из проверенного запуска с базовым путём. Параметры и границы проверки описаны в [инструкции по деплою](../../../docs/deploy.md#проверка-опубликованного-сайта); команда проверяет начальную страницу и ресурсы, а браузерные сценарии готовых функций выполняются отдельно. `just screenshots` ещё не реализован: следовать критерию соответствующей задачи и не считать его пройденным.
