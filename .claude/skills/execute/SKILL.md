# Выполнение пункта плана

Довести задачу с номером из `$ARGUMENTS` до проверенного результата. Выполнять именно указанный пункт, а не весь этап.

## Шаги

1. **Прочитать задачу и правила**
   - Найти номер и его `Проверка:` в [задачах](../../../docs/todos.md); сверить зависимости и цель с [планом](../../../docs/plan.md).
   - Прочитать [правила репозитория](../../../CLAUDE.md). Для изменения поведения свериться со [спецификацией](../../../docs/spec.md) и [дизайн-системой](../../../docs/design-system.md); открытые продуктовые решения — в [вопросах](../../../docs/questions.md).
   - Если номер отсутствует или решение невозможно вывести из документов, запросить нужное уточнение. Выбор способа реализации сделать самостоятельно.

2. **Реализовать пункт**
   - Размещать код по [структуре проекта](../../../docs/structure.md); соблюдать [стайлгайд](../../../docs/styleguide.md) и [дизайн-систему](../../../docs/design-system.md).
   - «Теория аудио» — статический сайт Astro с MDX, KaTeX, Shiki и Pagefind на GitHub Pages. Основной HTML создаётся при сборке, интерактивные элементы работают в браузере; ссылки и ресурсы учитывают базовый путь размещения. Демонстрационный рантайм макетов в приложение не переносится. Учитывать статусы инструментов в [техническом стеке](../../../docs/techstack.md).
   - Добавлять только нужные для пункта каталоги и зависимости. Новую переменную окружения описать в `.env.example` вместе с её первым использованием; секреты не записывать в Git.
   - После изменения кода сверить связанные документы с фактическим поведением и обновить устаревшие. Обновить `README.md`, если изменились статус, состав документов, требования к окружению или команды разработки.

3. **Проверить результат**
   - Для локальной проверки запускать из корня `just dev --host 127.0.0.1 --port 4321`. Фактический URL брать из вывода Astro: строка `Local` в обычном терминале или сообщение `Dev server running at` при фоновом запуске. Занятый порт может изменить адрес. В Claude Code запускать через `Bash` с `run_in_background: true`, сохранить ID задачи; читать вывод через `TaskOutput`. Если процесс остался в задаче, остановить его через `TaskStop` по этому ID и проверить завершение. Astro 7 автоматически запускает сервер агента в фоне и завершает команду: тогда сохранить PID и URL из вывода, проверить их через `npm run dev -- status`, читать логи через `npm run dev -- logs`. Перед остановкой снова сверить PID и URL через `status` с сохранёнными и только при совпадении выполнить из того же корня `npm run dev -- stop`, затем проверить `status`. Совместимый уже запущенный сайт можно использовать повторно; чужие процессы не останавливать и не заменять через `--force`. После своей проверки останавливать только собственный процесс; на время ожидаемой авторской проверки оставить его доступным. Не использовать массовые `pkill` или `killall`.
   - Статическую сборку проверять через `just build` (вызывает `npm run build`, результат — `dist/`).
   - `just build` также строит `dist/pagefind/` и проверяет локальные ссылки, HTML-якоря и ресурсы HTML/CSS без сетевой проверки внешних адресов; ошибка останавливает сборку. Фактические `base` и `outDir` учитываются при переопределении из CLI. Поиск по настоящему индексу проверяется полным `just test-e2e`; dev-сервер индекс не строит. Ручная проверка API на собранном сайте описана в [обзоре](../../../docs/overview.md#поисковый-индекс-и-проверка-артефакта). Проверки содержимого статей входят в `just build` и `astro build`: схема frontmatter, уникальность `slug`, якоря, Git-дата, источники, внутренние ссылки, язык листингов, идентификаторы и нумерация блоков (`assertValidArticles`), затем ссылки, якоря и ресурсы готового HTML. Отдельной команды для них нет; контрольные ошибки и изоляцию служебных статей проверяет `npm run test:articles`, он же выполняется в CI до `test:e2e`.
   - При изменении схемы, загрузки или целей треков выполнить `npm run test:tracks`: корректные служебные маршруты собираются в корне и под префиксом, неизвестная статья/раздел, повторный id элемента и пустой этап останавливают сборку; последующие обычные сборки подтверждают изоляцию фикстур от HTML, RSS, клиентских ресурсов и Pagefind. Служебные данные — `tests/fixtures/tracks/`, переменная `TRACKS_DIR` описана в `.env.example`; публичная сборка её не задаёт. Проверка также подтверждает обязательную запись «Новое» для публичного трека и «Черновик» без журнала в локальном режиме. При изменении журнала треков выполнить `npm run test:track-updates`: служебные сборки и Chromium/WebKit проверяют журнал, архив, фильтры, RSS, последние обновления, даты и ссылки этапов под обоими базовыми путями, в обеих темах и без JS. Эти фикстуры не публикуются. Команды сборки и `just typecheck` выполнять последовательно из-за общего кеша Astro.
   - При изменении обработки MDX, формул или их ресурсов выполнить `npm run test:mdx`: проверка собирает служебные материалы из `tests/fixtures/mdx/`, подтверждает MathML и локальные ресурсы, ошибку неверной формулы и отсутствие тестовых страниц в публичной сборке. Просмотр тестовой страницы описан в [обзоре](../../../docs/overview.md#проверка-mdx-и-формул).
   - При изменении схемы статей, групп или маршрутов выполнить `npm run test:articles`: проверка собирает служебные статьи из `tests/fixtures/articles/`, подтверждает маршрут из `slug`, отказ при повторном `slug`, неизвестной группе, пустых полях и неверном `readingMinutes`, отсутствие служебных статей в публичной сборке, «Черновик» для файла без коммита и ошибку публикуемой сборки без Git-даты, якоря `{#anchor}`, оглавление H2/H3 и ссылки на разделы под префиксом; повторный, неверный и неуместный якорь блокируют сборку; отсутствие источников, неверные ссылки и связанные темы, блок кода без языка, неверные идентификаторы и нумерация рисунков, таблиц и формул блокируют сборку, а превышение рекомендательных лимитов нет; в индекс Pagefind служебные статьи не попадают.
   - Выполнить именно проверку `Проверка:` из выбранного пункта, включая браузерную, редакционную, авторскую, CI или production-проверку, когда она там требуется.
   - Запустить подходящие проверки существующего приложения: `just fmt`, `just lint`, `just typecheck`, `just test`, `just build`. При изменении критичного пользовательского пути, доступности элементов или обработки адресов выполнить полный `just test-e2e`; отдельный файл не заменяет полный прогон. Новую предметную логику подтвердить осмысленными unit-тестами.
   - Доступны Prettier (`just fmt`, `npm run fmt:check`), ESLint (`just lint`), Astro Check и TypeScript (`just typecheck`), Vitest (`just test`) и Playwright (`just test-e2e`). Пропущенную проверку не считать пройденной; если критерий требует ещё не созданного сценария, соблюдать последовательность задачи.
   - Для создания или дополнения материалов вызвать `/write-article` через инструмент `Skill` с именем `write-article` и аргументами темы/уточнений. Передать тему из задачи, согласованный уровень объяснения и все ограничения пользователя, включая запрет коммита или публикации. Скилл читает [общие правила](../../../docs/authoring/rules.md) и [чеклист](../../../docs/authoring/checklist.md), готовит материал и возвращает файлы, локальные URL и результаты проверок. Затем продолжить этот процесс: выполнить критерий задачи и авторскую приёмку; коммит, отметка выполнения и публикация остаются его ответственностью и ждут предусмотренного одобрения. Для проверки уже подготовленных материалов прочитать общие правила и чеклист напрямую; повторно запускать подготовку без необходимости не нужно.
   - Для новой статьи или существенного дополнения опубликованной статьи подготовить запись журнала обновлений `src/content/updates/<id>.json` по [правилам журнала](../../../docs/authoring/rules.md#журнал-обновлений) и [шаблону](../../../docs/authoring/update-template.md); для исправления опечатки запись не нужна. Показать её автору вместе с материалом, в коммит включить только после одобрения. Неверная цель ссылки останавливает сборку.
   - Новую статью до коммита собирать так: `ALLOW_DRAFT_ARTICLES=1 just build` — страница показывает «Черновик» вместо даты (`just dev` включает этот режим сам). Обычный `just build` и CI без переменной требуют настоящей Git-даты коммита файла и полной истории: файл без коммита или неполный клон останавливают сборку. Переменную не задавать в CI и при публикации, требования к Git-датам не обходить. Проверить метаданные, внутренние ссылки и якоря.
   - Для визуализаций и аудио пройти раздел «Визуализация и аудио» [чеклиста](../../../docs/authoring/checklist.md#визуализация-и-аудио--если-добавлены-или-изменены): численные и граничные случаи, согласованность графика и звука, запуск действием пользователя, полный сброс и остановку при уходе со страницы. Автоматическая часть для `SamplingDemo` — сценарии `@sampling` в `tests/e2e/sampling-demo.spec.ts`, они входят в `just test-e2e`. Ручное прослушивание (щелчки, громкость) и проверку в настоящем Safari на Mac и iPhone выполняет автор: WebKit-тесты их не заменяют, результаты записываются отдельно от автоматических.
   - При изменении интерфейса посмотреть результат в браузере в состояниях и размерах из задачи и дизайн-системы. Исправить обнаруженные ошибки и повторить соответствующую проверку.

4. **Завершить**
   - Новые статьи, изменения их текста, записи журнала обновлений, определения глоссария и текст «О проекте» перед коммитом дать автору проверить на локальном сайте и доработать до явного одобрения. Уже полученное одобрение текущих правок действует; отсутствие ответа одобрением не считать.
   - Если обязательная проверка не прошла или недоступна, не отмечать задачу выполненной и не коммитить; назвать препятствие и уже проверенный результат.
   - После успешной проверки отметить пункт в `docs/todos.md` и закоммитить по скиллу `/commit`. Номер задачи в сообщение коммита не добавлять.
   - Не пушить для обычной локальной задачи. Если выбранный пункт прямо требует публикации, следовать [инструкции по CI и деплою](../../../docs/deploy.md), включая порядок коммита и пуша, авторское одобрение материалов и проверку деплоя нужного SHA.

## Адреса при локальной проверке

Конфигурация `src/site.config.ts` задаёт стандартный базовый путь `/audio-theory/`. Фоновый Astro может сообщать только origin без префикса: открывать сайт по origin и фактическому `base`, добавляя его ровно один раз. Для проверки корневого размещения использовать параметр `--base /` при запуске и сборке (`npm run build -- --base /`). Служебный маршрут MDX — `<origin><base>__test/mdx/`. Построитель `withBase` и обычные MDX-ссылки используют фактический базовый путь, включая переопределение из CLI.

## Браузерные проверки и DOM

`just test-e2e` последовательно собирает сайт в `.e2e/root/` и `.e2e/prefixed/`, затем запускает обязательный сокращённый набор Playwright: сценарии `@ci` в WebKit под префиксом, сценарии `@ci-cross-browser` в Chromium и Firefox под префиксом, сценарии `@placement` в Chromium в корне. Заметки «Подробнее» проверяются на той же служебной сборке сценариями `@margin-notes` из `tests/e2e/margin-notes.spec.ts` (маршрут `__test/margin-notes/`). Новые сценарии включаются в CI только явными метками; `node scripts/check-e2e-budget.mjs` проверяет лимит 88 обязательных E2E-проверок. Именно этот набор выполняется в CI; он является полным обязательным прогоном при изменении критичного пути. `just test-e2e-full` запускает прежнюю матрицу всех сценариев в трёх браузерах под обоими базовыми путями для диагностики. Правила выбора сценариев описаны в [обзоре](../../../docs/overview.md#браузерные-проверки). Перед первым запуском установить браузеры: `npx playwright install chromium firefox webkit` (для Linux CI — `npx playwright install --with-deps chromium firefox webkit`). Playwright управляет своими preview-серверами на 4391 и 4392; `--ignore-lock` оставляет их в foreground без общего lock-файла Astro, а `reuseExistingServer: false` запрещает использовать чужой сервер. Занятый порт означает ошибку проверки.

Сценарии DOM находятся в `tests/e2e/`, unit-тесты — в `tests/unit/`. Для исследования DOM доступны `page.locator()`, `page.getByRole()` и `page.evaluate()`; для снимка — `page.screenshot()`. Снимки и trace смотреть локальными средствами агента; WebKit не заменяет ручную проверку Safari. При порученной публикации после успешного деплоя нужного SHA выполнить `just test-production https://hazadus.github.io/audio-theory/`: передать фактический публичный URL окружения из проверенного запуска с базовым путём. Параметры и границы проверки описаны в [инструкции по деплою](../../../docs/deploy.md#проверка-опубликованного-сайта); команда проверяет начальную страницу и ресурсы, а браузерные сценарии готовых функций выполняются отдельно. `just screenshots` ещё не реализован: следовать критерию соответствующей задачи и не считать его пройденным.
