# План реализации

План первого выпуска «Теории аудио» опирается на [спецификацию](spec.md), [дизайн-систему](design-system.md), [стайлгайд](styleguide.md), [состав материалов](topics.md#статьи-первого-выпуска) и [выбранный стек](techstack.md). При расхождениях приоритет имеют спецификация, уточнения дизайн-системы, затем HTML-макеты.

В репозитории пока есть документация и макеты; приложения, статей и инфраструктуры сборки нет. Все этапы ниже предстоит выполнить. GitHub Pages настраивается на первом этапе: опубликованный сайт используется для проверки работы в реальных условиях по мере разработки. Первый полный выпуск включает весь согласованный объём; до него могут публиковаться готовые технические изменения и одобренные автором материалы.

## Результат первого выпуска

- Статический сайт на Astro с MDX, KaTeX и Shiki, опубликованный на GitHub Pages.
- Главная с тематическими группами, список материалов с фильтрами и сортировкой, страницы статей, глоссарий, поиск Pagefind, «О проекте» и 404.
- Светлая, тёмная и автоматическая темы; адаптивная вёрстка и доступное управление.
- Четыре проверенные автором статьи и один интерактивный пример дискретизации с прослушиванием восстановленного сигнала.
- Скиллы Codex и Claude Code с общими правилами подготовки и дополнения материалов.
- Команды `just`, автоматические проверки и деплой, воспроизводимый процесс локальной авторской проверки.

Примеры C++/JUCE развиваются после первого выпуска по мере необходимости. [Вопросы об их формате](questions.md#аудиоалгоритмы-и-примеры-кода) не блокируют этот план. Пагинация и другие функции вне спецификации требуют отдельного решения.

## Организация проекта

[Целевая структура](structure.md) описывает расположение будущих исходников, ресурсов и скиллов; этих файлов и каталогов пока нет. [Контракты данных и учебных компонентов](spec.md#данные-материалов-и-учебные-компоненты) находятся в спецификации. Этапы ниже описывают их реализацию и проверку.

## Этапы реализации

### 1. Подготовить приложение, команды и ранний деплой

1. Создать статический проект Astro, подключить MDX, TypeScript и обработку формул KaTeX при сборке. Зафиксировать версии зависимостей и lock-файл.
2. Настроить `site` и `base` для фактического репозитория GitHub Pages. Проверять также сборку под непустым префиксом, даже если основной адрес будет в корне домена.
3. Прочитать `~/Projects/table/justfile` и сохранить назначение команд из стайлгайда. `just` без аргументов выводит список с русскими комментариями.
4. Выбрать и настроить инструменты форматирования, линтинга, unit- и браузерных тестов. Рабочее предложение: Prettier, ESLint, Vitest и Playwright; эти инструменты пока не зафиксированы в `techstack.md`. При подключении записать фактический выбор туда.
5. Описать установку зависимостей и локальный запуск в корневом README. Если нужны переменные окружения, перечислить их только в `.env.example`, без секретов.
6. Настроить `just build` как сборку HTML, индекса Pagefind и проверку артефакта; первоначально команда проверяется на служебной странице. Реальные статьи добавляются на следующих этапах.
7. Сразу настроить `.github/workflows/pages.yml` и GitHub Pages: полная Git-история, зафиксированные зависимости, линтер, проверка типов, тесты, сборка HTML и Pagefind, проверка метаданных, ссылок и якорей, браузерная проверка готового каркаса. Только после успеха проверок публикуется тот же артефакт; настроить права workflow и защиту от конфликтующих деплоев. Проверки охватывают готовую часть и расширяются вместе с реализацией функций.
8. Опубликовать исходный каркас и настроить `just test-production` для проверки публичного адреса, страницы и ресурсов под фактическим базовым путём. На последующих этапах проверять готовые изменения через тот же деплой, добавляя production-проверки новых функций. Не публиковать непроверенные статьи и тестовые материалы.

**Готово, когда:** проект устанавливается из чистого checkout, `just dev` открывает локальный сайт, команды проверок выполняются, а каркас автоматически публикуется на GitHub Pages. `just test-production` подтверждает работу страницы и ресурсов по публичному адресу.

### 2. Реализовать коллекцию и проверку материалов

Зависит от этапа 1.

1. Реализовать схемы статей, групп, глоссария и ссылок по [контрактам спецификации](spec.md#данные-материалов-и-учебные-компоненты). Проверять уникальность slug и терминов, существование групп и внутренних целей.
2. Добавить вычисление Git-даты, времени чтения и стабильных якорей. Публичная сборка и локальный режим должны явно различать требования к дате нового файла.
3. Настроить рендеринг MDX, KaTeX и Shiki. Подсветка использует `--syntax-*`; формулы сохраняют доступное математическое представление. Неверная формула останавливает сборку.
4. Подготовить валидатор метаданных и контента: обязательные поля, источники, связанные темы, языки листингов, уникальные якоря, нумерация и ссылки.
5. Проверять внутренние ссылки по готовому HTML: страницы, ресурсы и якоря должны существовать. Внешние источники проверяются автором при подготовке текста; недоступность внешнего сайта не подменяет проверку внутренних ссылок.
6. Написать unit-тесты для расчёта времени чтения, Git-даты, разрешения ссылок и ошибочных метаданных. Временные материалы для тестов не включать в публикацию и поисковый индекс.

**Готово, когда:** корректный MDX рендерится, а неверные метаданные, отсутствующие страницы и якоря блокируют сборку; Git-дата и время чтения подтверждены тестами.

### 3. Собрать каркас и страницу статьи

Зависит от этапов 1–2.

1. Перенести токены «Лабораторной тетради» в общие CSS-файлы, разместить Literata, Golos Text и JetBrains Mono локально с лицензиями; подключить шрифты KaTeX и SVG-иконки Lucide.
2. Реализовать общую шапку, подвал, компактное меню, ссылку перехода к содержимому, активные пункты и кнопку «Наверх». Ссылки GitHub и Issues берутся из конфигурации репозитория.
3. Реализовать три темы, раннее восстановление выбора до CSS, реакцию авто на системную тему и работу при отказе `localStorage`. Без JavaScript действует системная тема средствами CSS.
4. Собрать страницу статьи: заголовок-вопрос, метаданные, хлебные крошки, теги, оглавление H2/H3 и прогресс чтения по телу статьи. На узких экранах оглавление раскрывается; на широких закреплено и выделяет текущий раздел.
5. Реализовать учебные компоненты, доступные подсказки терминов, оформление таблиц и рисунков, копирование кода и адресов разделов. Сообщать успех только после успешной операции clipboard.
6. Проверить сетку по макетам: колонка текста 680 px, широкие блоки до 880 px, оглавление 240 px; локальная прокрутка кода, таблиц и длинных формул. Соблюдать уточнения промежуточных ширин из дизайн-системы.

**Готово, когда:** служебный образец статьи показывает все учебные блоки в обеих темах на 390 и 1440 px, не создаёт горизонтальной прокрутки страницы и читается без JS. Меню, оглавление, подсказки и копирование проверены клавиатурой, включая ошибки и возврат фокуса.

### 4. Подготовить общий скилл и первые тексты

Зависит от этапов 2–3; завершается до подготовки поискового попапа и итогового контента.

1. Создать `docs/authoring/rules.md`, `checklist.md` и `article-template.mdx`. Общие правила описывают выбор между дополнением и новой статьёй, изучение существующих материалов, работу с источниками, терминами, ссылками, формулами, компонентами и проверками.
2. Создать тонкие точки входа `.agents/skills/write-article/SKILL.md` и `.claude/skills/write-article/SKILL.md`. В обеих указать обязательное чтение `docs/authoring/rules.md` и чеклиста относительно корня репозитория; не копировать туда редакционные правила. Параметр запуска — тема и необязательные уточнения уровня объяснения.
3. Проверить обнаружение скилла и чтение общего набора правил в обоих агентах. В README описать фактический вызов и процесс дополнения статьи.
4. В общие правила включить обязательную проверку текста по актуальному [tropes.md](https://tropes.fyi/tropes-md), с исправлением русскоязычных аналогов шаблонных оборотов до передачи автору. Также проверять техническую точность, согласованность расчётов и отсутствие дублирования.
5. С помощью скилла создать первые статьи `sound-wave.mdx` и `sampling.mdx` в группах `basics` и `digital`. Подготовить проверенные источники, явные якоря и начальные записи глоссария. В дискретизации пока использовать корректный статичный рисунок; взаимодействие и звук добавляются на этапе 7.
6. Проверить обе статьи на локальном сайте и провести первые доработки по вопросам автора. До одобрения не включать материалы в публикуемый коммит.

**Готово, когда:** оба агента используют общий набор правил, две статьи созданы этим процессом и пригодны для проверки реального поискового индекса. Авторские доработки продолжаются до итогового одобрения.

### 5. Проверить Pagefind и реализовать поиск

Зависит от этапа 4. Проверка реального индекса обязательна до полной реализации попапа.

1. Собрать индекс по первым статьям. Выделить содержимое для индексации, исключить шапку, подвал, меню и элементы управления; после появления глоссария включить его определения.
2. Проверить через API Pagefind русский текст и словоформы, английские термины внутри русскоязычных страниц и результаты по разделам. Зафиксировать запросы, ожидаемые статьи и якоря в браузерных тестах.
3. Проверить загрузку индекса и переходы под префиксом GitHub Pages. Если проверка выявит ограничение, сначала исправить интеграцию и повторить проверку; необходимое изменение требований вынести в `questions.md` и согласовать до продолжения зависимых работ.
4. Реализовать собственный попап поверх Pagefind: пустой запрос, загрузка, результаты, отсутствие результатов и ошибка с повтором. Устаревший ответ не заменяет результат нового запроса; фрагменты подсвечиваются безопасно.
5. Добавить открытие кнопкой и `/`, навигацию `↑`/`↓`/`Enter`, `Esc`, закрытие по фону, блокировку фонового взаимодействия и прокрутки, ограничение фокуса и его возврат. Горячие клавиши учитывают поля ввода, редактируемые области, модификаторы и композиционный ввод.
6. Проверить полноэкранный вариант на смартфоне, экранную клавиатуру, safe-area и прокрутку выбранного результата. Без JS показывать пояснение и ссылку на все материалы.

**Готово, когда:** реальные запросы находят ожидаемые статьи и разделы, результаты ведут по существующим адресам, а все состояния и клавиатурные сценарии работают в обеих темах.

### 6. Реализовать остальные страницы

Зависит от этапов 3–5.

1. Создать главную `/` по варианту 2b: четыре группы, описания, до четырёх последних обновлённых статей в группе, «Все N» и кнопка поиска. Пустые группы скрываются; одна статья в группе остаётся видимой.
2. Создать `/materials/` по варианту 2a. Фильтр `topic` использует идентификатор основной группы, сортировка `sort` — `date`, `alpha`, `topic`; по умолчанию дата по убыванию. При равных датах и внутри групп действует стабильный порядок по русскому названию.
3. Сохранять фильтр и сортировку в URL, восстанавливать их при перезагрузке и переходах назад/вперёд. Неверные значения заменять значениями по умолчанию. Проверить пустые группы и счётчики; без JS доступен полный список по дате.
4. Создать `/glossary/` по единому источнику: сортировка по русскому названию, английское название, определение, стабильный якорь и подробное объяснение. Подсказки статьи берут тот же текст; Pagefind индексирует глоссарий.
5. Создать `/about/` с назначением, описанием проверки материалов и разделом предложений через Issues. Текст передать автору на проверку.
6. Создать `404.html`: понятная ошибка, текущий неверный путь как текст, ссылки на главную и поиск. При доступном индексе искать подсказки по словам пути; ошибка поиска не мешает основным действиям.

**Готово, когда:** все маршруты доступны под базовым путём, навигация согласована, список проверен на 0, 3 и большом наборе тестовых статей. Глоссарий и расширенная навигация проверены визуально, поскольку их полного макета нет.

### 7. Реализовать эксперимент дискретизации и звук

Зависит от этапов 3–4; после подготовки страницы статьи может выполняться независимо от завершения этапов 5–6.

1. Вынести расчёты в чистые функции: исходная синусоида, моменты отсчётов, значения, период дискретизации и частота результата. Статичный SVG при сборке и интерактивный график используют одну модель.
2. Сохранить параметры макета: сигнал 1 кГц, интервал 0–3 мс, начальная частота дискретизации 8 000 Гц, диапазон 1 000–16 000 Гц, шаг 100 Гц; кнопки 1,5, 2 и 8 кГц, показ алиасинга и полный сброс.
3. Проверить случаи ниже, на границе и выше частоты Найквиста. Отдельно разобрать вырожденные отсчёты при выбранной фазе, в том числе при 1 и 2 кГц; на границе не обещать однозначное восстановление. Проверять совпадение отсчётов исходного сигнала и показанного результата, включая фазу и знак.
4. Явно объяснить модель восстановления и её упрощения. График, легенда, статус, период, число отсчётов, подпись и аудио должны описывать один результат. Частота дискретизации эксперимента не подменяется аппаратной частотой `AudioContext`.
5. Добавить ползунок, кнопки ключевых значений, переключатель и сброс. SVG адаптирует геометрию и деления без уменьшения текста; значения доступны мышью, касанием и клавиатурой либо через равноценное текстовое представление.
6. Добавить конечный звуковой фрагмент восстановленного сигнала через Web Audio: длительность и позиция, воспроизведение, пауза, остановка, перемотка, громкость и mute. Начальный уровень регулятора — 30 %, плавное нарастание и затухание около 20 мс, видимое предупреждение перед чистыми тонами. Длительность фрагмента задаётся отдельно от 3 мс, показанных на графике.
7. Согласовать поведение смены параметров: останавливать текущий фрагмент и сбрасывать позицию, затем создавать результат для новых значений по следующему нажатию воспроизведения. Уход со страницы останавливает звук; сброс возвращает все параметры и состояние плеера.
8. Проверить клавиши плеера без перехвата управления ползунками. При отсутствии или ошибке Web Audio график продолжает работать; при отсутствии JS остаются рисунок, объяснение и неактивные контролы с понятным сообщением.

**Готово, когда:** unit-тесты подтверждают численные и граничные случаи, взаимодействие и состояния проверены в браузере, график и звук согласованы. Прослушивание и управление проверены вручную в настоящем Safari на Mac и iPhone.

### 8. Завершить четыре статьи и глоссарий

Зависит от этапов 4, 6–7.

| Файл и маршрут | Статья | Группа |
| --- | --- | --- |
| `sound-wave.mdx` → `/sound-wave/` | Звуковая волна и аналоговый аудиосигнал | `basics` |
| `sampling.mdx` → `/sampling/` | Дискретизация: отсчёты, период и частота дискретизации | `digital` |
| `adc-dac.mdx` → `/adc-dac/` | АЦП и ЦАП | `conv` |
| `audio-data.mdx` → `/audio-data/` | Аудиоданные в программах: представление отсчётов, каналы, кадры и буферы | `data` |

1. Завершить первые две статьи и создать остальные две через скилл. Согласованное распределение тем сохраняется; темы не превращаются автоматически в отдельные статьи.
2. Встроить эксперимент в статью о дискретизации. Другие рисунки создавать как статичные SVG там, где они помогают объяснению; дополнительные интерактивные примеры не нужны для завершения выпуска.
3. Заполнить глоссарий основными терминами статей. Проверить первое упоминание русских и английских названий, единицы, обозначения и определения во всех материалах.
4. Проверить источники, предварительные знания и связанные темы; заменить временные ссылки на Википедию внутренними только для реально добавленных материалов и существующих разделов.
5. Выполнить редакционную проверку по tropes.md, расчёты и сборку. Передать автору статьи на локальном сайте и дорабатывать их до одобрения каждой статьи. Проверить также определения глоссария и текст «О проекте».

**Готово, когда:** четыре статьи покрывают темы первого выпуска, не дублируют объяснения без необходимости, прошли техническую и редакционную проверку и лично одобрены автором.

### 9. Проверить полный выпуск

GitHub Pages и workflow работают с этапа 1. Завершение первого полного выпуска зависит от готовности этапов 1–8 и авторского одобрения контента.

1. Проверить полноту обязательных проверок CI для всего выпуска: линтер, типы, unit-тесты, сборка сайта и Pagefind, метаданные, внутренние ссылки и якоря, основные браузерные сценарии. Убедиться, что ошибка любой проверки блокирует деплой и публикуется тот же проверенный артефакт.
2. Проверить Git-даты четырёх статей в опубликованной сборке и настройки существующего workflow. Непроверенные материалы не включать в публикуемый коммит.
3. Реализовать `just screenshots` для страниц и основных состояний в обеих темах на 390 и 1440 px. Дополнительно проверить 320 px и границы 599/600, 1023/1024, 1279/1280 px, увеличенный текст и масштаб.
4. Запускать сквозные тесты на собранном сайте с настоящим индексом Pagefind, включая сборку под префиксом. Проверять чтение, навигацию, историю фильтра, поиск, тему и визуализацию; WebKit в CI дополняет ручную проверку настоящего Safari.
5. До публикации проверить Safari на macOS и iOS в первую очередь, затем Chrome и Firefox на компьютере и Chrome на Android. Проверить клавиатуру, фокус, отсутствие JS, отказ storage и clipboard, ошибку поискового индекса и недоступность аудио.
6. После одобрения итоговых изменений выполнить коммит и пуш в основную ветку без обязательного PR. Проверить успешный CI и деплой, затем полный `just test-production` по публичному адресу: страницы, ресурсы, реальный поиск, якоря и фактическую страницу 404 GitHub Pages.
7. Описать регулярный процесс: запрос темы → скилл → локальная проверка → доработки → одобрение → коммит и пуш → CI и деплой → smoke-проверка. При ошибке обязательных проверок публикация останавливается до исправления.

**Готово, когда:** сайт опубликован, обязательные проверки проходят, браузерная и авторская проверка завершены, smoke-проверка подтверждает работу публичного сайта.

## После готовности основной части

После завершения и публикации первого выпуска рассмотреть [RSS-ленту статей](idea.md#после-готовности-основной-части-rss). Предлагаемый подход — формировать ленту при сборке и публиковать вместе с сайтом; отдельно согласовать состав записей и объём текста. Эта идея не блокирует готовность основной части и не входит в обязательные этапы выше.
