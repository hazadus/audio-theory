# Спецификация проекта

Документ фиксирует согласованные требования. Замысел и предложения для обсуждения находятся в [idea.md](idea.md), темы — в [topics.md](topics.md), варианты технологий — в [techstack.md](techstack.md), открытые вопросы — в [questions.md](questions.md).

Общие соглашения о коде, языке, конфигурации и сообщениях коммитов собраны в [styleguide.md](styleguide.md). Целевая структура проекта — в [structure.md](structure.md), этапы работ — в [plan.md](plan.md).

## Назначение и название

- Сайт предназначен прежде всего для личного изучения теории аудио; материалы также могут читать друзья пользователя.
- Рабочее название — «Теория аудио». Название не принципиально и может быть изменено.

## Сайт

- Статический сайт со статьями и визуализациями по теории аудио и цифровой обработке звука.
- Статический генератор — Astro. Страницы создаются при сборке; опубликованный сайт работает без серверной части.
- Удобная вёрстка для десктопа и смартфонов.
- Переключение темы оформления между светлой, тёмной и автоматической. В автоматическом режиме тема следует системным настройкам пользователя.
- Автоматический деплой на GitHub Pages.
- Адреса статей — английские, по названию понятия, например `/sampling/` и `/buffer-size/`.
- Репозиторий публичный; предложения тем и исправлений принимаются через GitHub Issues. Ссылка на репозиторий подписывается «GitHub».

## Первый выпуск

- В первый выпуск входит полный набор согласованных функций сайта: главная, список материалов с фильтрами и сортировкой, страницы статей, каталог и страницы пяти треков чтения, глоссарий, поиск, страницы «О проекте» и 404, журнал обновлений с архивом по годам и RSS-лентой, темы оформления и автоматический деплой на GitHub Pages.
- Стартовый контент — пять статей: «Звуковая волна и аналоговый аудиосигнал»; «Кривые равной громкости: как частота и уровень звука влияют на восприятие»; «Дискретизация: отсчёты, период и частота дискретизации»; «АЦП и ЦАП»; «Аудиоданные в программах: представление отсчётов, каналы, кадры и буферы». Распределение тем описано в [topics.md](topics.md#статьи-первого-выпуска).
- Первый выпуск включает интерактивный пример в статье о дискретизации. За основу берётся блок «Отсчёты синусоиды при разной частоте дискретизации» из [макета статьи](design/3-article.html): график, параметры, легенда, состояния и мобильный вариант с уточнениями [дизайн-системы](design-system.md#визуализации-и-аудио). Согласованное прослушивание восстановленного сигнала дополняет график; его реализация следует правилам аудио из дизайн-системы. Статья о звуковой волне содержит генератор чистого тона в разделе о частоте: синус 20 Гц – 20 кГц по логарифмической шкале с периодом и длиной волны выбранной частоты, звучит непрерывно до остановки, частота меняется во время звучания. Там же визуализация фазы без звука: окружность с векторами и две синусоиды 1 кГц, начальная фаза сдвинутой меняется от 0 до 360° с шагом 15°.
- Скилл подготовки и дополнения материалов для Codex и Claude Code входит в первый выпуск; первые статьи создаются с его помощью.
- Примеры C++/JUCE не входят в обязательный объём первого выпуска; они добавляются по мере необходимости.

## Команды разработки

- В корне проекта настраивается `justfile` по аналогии с `~/Projects/table/justfile`, чтобы привычные команды сохраняли названия и назначение при переключении между проектами.
- Команды: `dev`, `fmt`, `lint`, `typecheck`, `test`, `test-e2e`, `test-production`, `screenshots`, `build`. Их назначение описано в [styleguide.md](styleguide.md#команды-разработки).
- Вызов `just` без аргументов показывает список доступных команд. Комментарии к командам пишутся на русском; внутренние команды адаптируются к стеку этого проекта.

## Страницы и навигация

- Главная — кнопка поиска, блок «С чего начать» с пятью треками, раздел «Интерактивные визуализации» (карточки по [макету](design/8-demos-on-home.html), реестр `src/data/visualizations.ts`), блок «Недавно на сайте» после визуализаций и тематические группы с карточками статей (вариант 2b из [макета страниц](design/4-pages.html)). Если визуализаций больше четырёх, главная показывает первые четыре и «Все N» со ссылкой на страницу `/visualizations/` со всеми карточками.
- Исходные группы: «Основы звука», «Цифровой сигнал», «АЦП и ЦАП», «Аудиоданные в программах». Группа «Обработка звука» добавлена по [issue #1](https://github.com/hazadus/audio-theory/issues/1), группа «Синтез» (`synthesis`, «Осцилляторы, огибающие и фильтры синтезатора») — по [issue #15](https://github.com/hazadus/audio-theory/issues/15) для серии статей о базовом одноголосном синтезаторе. Агент может предложить новую группу; её добавление согласовывает автор.
- «Все материалы» — отдельная страница со списком статей, фильтрами по темам и сортировкой по дате обновления, названию или теме. Фильтр и сортировка сохраняются в URL.
- Глоссарий — отдельная страница; определения для него и подсказок терминов берутся из единого источника.
- Также предусмотрены страницы статьи, «О проекте» и 404.
- Статьи связываются предварительными знаниями, перекрёстными ссылками и связанными темами; глобальной навигации «предыдущая / следующая статья» нет; при открытии из трека доступны соседние элементы этого трека.

## Дизайн

- Визуальный характер сайта определяет дизайнер.
- Компоновку страницы статьи и оформление её содержимого предлагает дизайнер с учётом требований к материалам и адаптации для десктопа и смартфонов.
- Принято направление «Лабораторная тетрадь»: Literata для текста и основных заголовков, Golos Text для интерфейса, JetBrains Mono для кода; словесный знак «Теория аудио», иконки Lucide.
- На странице статьи под шапкой показывается индикатор прогресса чтения высотой 2 px.
- Правила реализации UI и уточнения к макетам собраны в [design-system.md](design-system.md).

## Материалы

- Все материалы пишутся на русском языке.
- Единый формат исходников статей — MDX: текст пишется в Markdown, визуализации и учебные блоки подключаются готовыми компонентами. HTML страниц создаётся при сборке.
- Блоки кода с указанным языком получают подсветку синтаксиса через встроенный в Astro Shiki при сборке. Цвета используют токены дизайн-системы и следуют светлой, тёмной и автоматической теме; подсветка работает без JavaScript в браузере.
- При первом упоминании основного понятия или термина в каждой статье приводится его английское название в скобках после русского: например, «частота дискретизации (sample rate)» или «аналого-цифровой преобразователь (analog-to-digital converter, ADC)». При последующих упоминаниях повторять английское название не обязательно.
- Основные термины при введении или определении всегда оформляются компонентом `Term` со ссылкой и подсказкой из глоссария. Если записи ещё нет, она добавляется вместе со статьёй.
- Основной формат — самостоятельные статьи. Последовательное прохождение курса не требуется.
- По умолчанию объяснения начинаются с основ. Пользователь может уточнить для агента нужный уровень конкретного материала.
- Интерактивные элементы добавляются там, где действительно помогают лучше понять материал. Они не обязательны для каждой статьи.
- Одна статья может раскрывать несколько связанных тем. Запрос новой темы не означает обязательного создания отдельной статьи.
- Обязательные элементы статьи: заголовок с названием понятия, подзаголовок-вопрос, метаданные (дата публикации, дата последнего содержательного дополнения при его наличии, время чтения, теги тем), источники и связанные темы. Остальная структура зависит от объяснения.
- Под заголовком статьи показываются только «Опубликовано» и, при наличии содержательных дополнений, «Дополнено» со ссылкой на запись журнала. Отдельная Git-дата «Обновлено» в статье не выводится. В карточках и списке материалов дата обновления — последнее содержательное дополнение из журнала, а без дополнений — публикация. По ней сортируются материалы и карточки в тематических группах главной; исправление опечатки порядок не меняет.
- При локальном просмотре новой статьи без коммита вместо даты показывается «Черновик».
- Статья рассчитана на печать из браузера. В печатной версии нет шапки, подвала, хлебных крошек, оглавления, поиска, кнопки «Наверх», навигации по треку и элементов управления демонстраций; палитра светлая независимо от выбранной темы, основной шрифт 10pt. Рисунки, таблицы, формулы, врезки, блоки кода и демонстрации переносятся на следующую страницу целиком, подпись остаётся с рисунком, заголовок не стоит последней строкой страницы. Длинные строки кода переносятся. Адреса внешних ссылок рядом с текстом не печатаются.
- Оценка времени чтения: число слов текста / 180 слов в минуту, округление вверх, минимум 1 минута. Листинги кода и математическая разметка не учитываются; для сложной статьи автор может задать ручную поправку.
- Числовые ограничения из руководства дизайнера (например, 1–3 тега, до 4 врезок, до 25 строк кода) — рекомендации, а не жёсткие ограничения.
- Синтетические аудиопримеры создаются в браузере через Web Audio; аудиофайлы используются для записей. Звук запускается действием пользователя.
- По [issue #5](https://github.com/hazadus/audio-theory/issues/5) добавляется самостоятельная статья `/lfo/` в группе «Обработка звука»: смысл низкой частоты, применения LFO, фазовый аккумулятор и перенос фазы, формулы синусоидальной, треугольной, прямоугольной и пилообразной волн. Примеры C++ показывают генерацию без JUCE и с `juce::dsp::Oscillator` стабильной версии 9.0.3, применение к усилению кратко поясняется со ссылкой на статью о тремоло; в статье используются статичные SVG и существующие учебные компоненты.
- По [issue #8](https://github.com/hazadus/audio-theory/issues/8) подробный пример тремоло из `/lfo/` вынесен в `/tremolo/`: сравниваются усиление `1 − D(1 + l)/2` с диапазоном `1 − D…1` и `1 + Dl` с диапазоном `1 − D…1 + D`, объясняются глубина, фазовое различие и запас уровня. Статичные SVG показывают сигнал до/после, шаги преобразования LFO при глубине 40 % и обе шкалы глубины; самостоятельный листинг C++/JUCE обрабатывает все каналы одним значением LFO на кадр. Адреса `/lfo/#tremolo` и `/lfo/#eq-tremolo` сохранены и ведут к ссылкам на подробное объяснение.
- По [issue #6](https://github.com/hazadus/audio-theory/issues/6) статичный рис. 2 статьи `/lfo/` (`#lfo-waveforms`) заменён визуализацией без звука «Четыре формы LFO из одной фазы»: окружность фазы и четыре графика одного цикла −π…π (синусоида, треугольник, прямоугольник, пила) с вертикальным курсором текущей фазы, отметкой значения и расчётом по формуле статьи над каждым графиком. Фазу меняют перетаскиванием точки на окружности (мышь, касание), ползунком −180…179° с шагом 1° и кнопками −π, −π/2, 0, π/2; кнопка «Запустить / Пауза» вращает фазу со скоростью один оборот за 4 с, ручное изменение и «Сбросить» её останавливают, сброс возвращает −45°. Анимация запускается только кнопкой и останавливается при скрытии вкладки или уходе со страницы.
- По [issue #7](https://github.com/hazadus/audio-theory/issues/7) добавляется самостоятельная статья `/audio-math/` в группе «Основы звука»: математический минимум для чтения существующих материалов. Она объясняет обозначения, единицы и отношения, степени, корни и модуль, функции и графики, радианы, синус и косинус, логарифмы и экспоненту, суммы и RMS, кусочные функции, округление, sinc и рекуррентные формулы на числовых примерах из аудио. Существующие статьи ссылаются на соответствующий математический разбор.
- По [issue #10](https://github.com/hazadus/audio-theory/issues/10) добавляется обзорная статья `/psychoacoustics/` в группе «Основы звука»: порог слышимости и слуховая область, громкость в сонах (фоны и кривые равной громкости остаются в `/equal-loudness/`), высота тона, критические полосы, частотная и временная маскировка, межушные разности времени и уровня, перцептивное кодирование MP3 и AAC. Иллюстрации — статичные SVG: порог слышимости по ISO 226:2023, модель порога маскировки тоном 1 кГц и схема пред- и постмаскировки; интерактивных примеров, звука и карточки на главной нет. Термины «порог слышимости» и «слуховая маскировка» в глоссарии ведут в новую статью.
- По [issue #11](https://github.com/hazadus/audio-theory/issues/11) добавляется самостоятельная статья `/wav-file/` в группе «Аудиоданные в программах»: порядок байтов little-endian, контейнер RIFF, устройство чанка и байт выравнивания, поля `fmt ` и их вывод, `data` и длительность, чтение по чанкам без расчёта на заголовок в 44 байта, служебные чанки `JUNK`, `bext`, `LIST`/`INFO` и частные, запись минимального файла, ограничения 4 ГБ (RF64) и `WAVE_FORMAT_EXTENSIBLE`. Примеры C++ без библиотек (разбор и запись) и чтение через `juce::AudioFormatManager` / `AudioFormatReader`. Кодирование отдельного отсчёта (знак, 24 бита, перевод в `float`) разбирается отдельно. В статье визуализация без звука «Байты WAV-файла по полям» (`#wav-dump`): учебный файл из 122 байт (`RIFF`, `JUNK` на 28 байт, `fmt ` для 16 бит, стерео, 44,1 кГц, `data` с четырьмя кадрами, `LIST`/`INFO` с чанком `INAM` нечётного размера и байтом выравнивания) показан дампом по 8 байт в строке со смещением и колонкой ASCII. Поле выбирают наведением мыши или нажатием на байт, стрелками и Home/End в дампе, кнопками чанков на карте и «Предыдущее / Следующее поле»; описание показывает чанк, имя поля, смещение, байты, чтение значения и смысл. «Сбросить» возвращает первое поле. В «Математику для аудио» добавлен раздел о двоичной и шестнадцатеричной записи (`#number-bases`).

- По [issue #12](https://github.com/hazadus/audio-theory/issues/12) добавлена самостоятельная статья `/integer-pcm/` в группе «Аудиоданные в программах»: диапазоны 8/16/24/32 бит, дополнительный код, WAV u8 со смещением 128, чтение little-endian, расширение знака 24 → 32 бита, варианты нормирования, обратная запись с округлением и ограничением диапазона, точность binary32 и дизеринг. Примеры C++17 (вариант со сдвигами — C++20) и `juce::AudioData` версии 9.0.3. Визуализация без звука `#pcm-sample` разбирает одно знаковое 24-битное целое либо три hex-байта little-endian: биты, знак, расширенный код и `float` при масштабе 8388608. Начальное значение и сброс — −256; ввод применяется кнопкой или Enter; неверный ввод сохраняет последний корректный разбор и сообщает ошибку. Без JS показан статичный разбор и неактивный ввод. В `audio-data` остаётся краткая ссылка на подробное объяснение; математическая справка дополнена побитовыми операциями.

- По [issue #14](https://github.com/hazadus/audio-theory/issues/14) добавлена самостоятельная статья `/audio-compression/` в группе «Аудиоданные в программах»: битрейт несжатого PCM, сжатие без потерь и с потерями, AIFF и AIFF-C в сравнении с WAV (big-endian, `COMM`, 80-битная частота, `SSND`), FLAC (блоки, фиксированные предсказатели порядков 0–4 и LPC, коды Райса, середина и разность, `STREAMINFO` и MD5, кадры), MP3 (гибридный банк фильтров и MDCT, психоакустическая модель, переключение окон, квантование и коды Хаффмана, кадр и заголовок, битовый резервуар, CBR/VBR, совместное стерео, ID3, артефакты) и краткое сравнение с AAC, Opus и ALAC. Связь MP3 с психоакустикой показана таблицей блоков кодера и ссылками на разделы `/psychoacoustics/`; теория маскировки не пересказывается, у `/psychoacoustics/` и `/wav-file/` добавлены обратные ссылки. Визуализация без звука `#flac-prediction` кодирует 32 отсчёта 16 бит (тон 1 кГц, тон 5 кГц или шум) фиксированным предсказателем порядка 0–4: графики отсчётов с предсказанием и остатка, лучший параметр Райса, размер подкадра по слагаемым относительно записи без сжатия и коды первых четырёх остатков. Начальное состояние и сброс — тон 1 кГц, порядок 2; без JS показан статичный расчёт и неактивные параметры. Математическая справка дополнена разделами о целочисленном делении с остатком и о разностях соседних значений.

- По запросу автора добавляется статья `/mixing/` «Микширование сигналов: усиление, фаза и запас уровня» в группе «Обработка звука»: краткое рабочее представление float, независимые gain, сумма двух источников, фазовое сложение, headroom, gain staging и защита выхода без повторения кодера PCM. Примеры C++17 и JUCE 9.0.3. Визуализация без звука `#mixing-demo` показывает два вклада, сумму и ограничение до ±1 на протяжении двух периодов; gain каждого источника 0…1 с шагом 0,05, разность фаз 0…360° с шагом 15°. Начальное состояние и сброс: gain 0,5 и 0,5, фаза 0°; пример «Перегрузка»: 0,8 и 0,8, 0°; «Противофаза»: 0,5 и 0,5, 180°. Амплитуда суммы вычисляется аналитически; без JS и при ошибке остаётся начальный график с неактивными параметрами. В треке программиста статья стоит перед LFO и тремоло.

- По запросу автора добавляется статья `/noise/` «Белый и розовый шум: спектр и генерация» в группе «Обработка звука»: PRNG и физическая случайность, seed и воспроизводимость, равномерные отсчёты, PSD белого шума и закон `1/f` для розового, Voss–McCartney, среднее и DC offset, peak/RMS/headroom и отличие от TPDF-дизеринга. Примеры — C++20/JUCE 9.0.3 с состоянием между блоками. Эксперимент `#noise-demo` показывает первые 128 отсчётов, усреднённую PSD и мощность октав двух фрагментов по 4 с при 48 кГц и RMS 0,12; начальный seed 2026, допустимые seed — целые 0…4294967295. Прослушивание выбранного шума имеет паузу, остановку, перемотку, громкость и mute; выбор seed или цвета останавливает звук и сбрасывает позицию. Полный сброс возвращает seed 2026, белый шум, позицию 0 и громкость 30 %. Без JS остаются исходные графики и значения. Математическая справка дополнена вероятностью, ожиданием и смыслом PSD; в треке программиста статья идёт после тремоло.

- По [issue #15](https://github.com/hazadus/audio-theory/issues/15) добавлена статья `/synth-oscillators/` «Осцилляторы синтезатора: формы, расстройка и саб-осциллятор» — первая в группе «Синтез» и в серии из четырёх статей о синтезаторе, который рендерит одну ноту в WAV. Схема голоса (компонент `SynthChain`, источники → микшер → фильтр НЧ → VCA ← ADSR → WAV) повторяется в каждой статье серии с выделением разбираемой части. Статья различает осциллятор и осциллограф, объясняет отдельную фазу каждого осциллятора в долях периода, гармоники форм и отражения пилы при 48 кГц для A2 и A6, двухточечную поправку PolyBLEP для пилы и прямоугольника (треугольник и синус без поправки), частоту ноты MIDI при A4 = 440 Гц, интервалы, расстройку в центах и биения гармоник, саб-осциллятор на октаву ниже (отдельный аккумулятор или деление фазы, общий сброс в начале ноты), шум как четвёртый источник и микшер с худшей оценкой пика Σ|gᵢ|. Примеры C++20 (`Oscillator`, `VoiceSources`, `VoiceLevels`) и заполнение `juce::AudioBuffer` JUCE 9.0.3. Визуализация со звуком `#voice-sources` «Источники голоса: сумма, спектр и пик»: нота MIDI 21–105, форма и уровень двух осцилляторов, интервал второго (унисон, квинта, октава) и расстройка −50…+50 центов, форма и уровень саба, цвет и уровень шума, PolyBLEP и показ вкладов источников. Начальное состояние и сброс: A3, пила 0,35 и пила 0,35 в унисоне +7 центов, саб-прямоугольник 0,2, белый шум 0, PolyBLEP включён, вклады скрыты, звук остановлен, громкость 30 %. Примеры: «A6 без PolyBLEP», «Квинта без расстройки», «Перегрузка» (0,6, 0,6, 0,4 и шум 0,2). Графики при 48 кГц от начала ноты: четыре периода суммы и её спектр (16 384 отсчёта, окно Блэкмана — Харриса, логарифмическая шкала 20 Гц — 24 кГц) с кольцами на отражённых составляющих: самая сильная в каждой из шести частей полосы 20 Гц — 5 кГц с равным отношением частот, кроме лежащих ближе 18 Гц к гармоникам. Статус показывает частоты, биения совпадающих гармоник, пик суммы за 2 с и худшую оценку в dBFS, предупреждение при выходе за 0 dBFS и сильнейшее отражение. Звук считается тем же кодом непрерывно до остановки: блоки по 2048 кадров планируются с опережением, уровни меняются линейно за 20 мс, смена формы, цвета шума или PolyBLEP проходит через затухание и нарастание за 20 мс, частоты меняются без сброса фаз; уход со страницы и скрытая вкладка останавливают звук. Без JS остаются исходные графики, статус и подпись. Математическая справка дополнена полутонами и центами и биениями; в треке программиста предлагается новый этап «Синтезатор».

## Данные материалов и учебные компоненты

Целевая организация исходников описана в [structure.md](structure.md); порядок реализации — в [plan.md](plan.md).

### Данные статей и ссылки

| Поле | Контракт |
| --- | --- |
| `slug` | Обязательный уникальный английский идентификатор в kebab-case; задаёт маршрут `/<slug>/` |
| `title` | Название понятия на русском |
| `question` | Подзаголовок-вопрос |
| `topic` | Одна основная группа: `basics`, `digital`, `conv` или `data` |
| `tags` | Непустой список русских тегов для дополнительных связей; предел 1–3 не является жёстким |
| `prerequisites` | Необязательный список ссылок с пояснениями |
| `related` | Обязательный непустой список связанных понятий с пояснениями |
| `readingMinutes` | Необязательное положительное целое число, заменяющее автоматическую оценку |

Для `prerequisites` и `related` использовать записи `{ label, description, target }`. Внутренняя цель — `{ article, anchor? }`, где `article` соответствует `slug`; внешняя — `{ url }`. Для отсутствующего материала используется соответствующая статья Википедии. Источники остаются разделом MDX со ссылками; проверка контента требует раздела `## Источники {#sources}` хотя бы с одной ссылкой. Поля `updated` во frontmatter нет.

Группы хранят `id`, русское название, описание и порядок вывода из дизайн-системы. Глоссарий хранит записи `{ id, ru, en, definition, target }`: `id` задаёт стабильный английский якорь, а `target` использует тот же контракт ссылок. Определение — короткий текст без произвольного HTML; глоссарий и подсказки читают одну запись.

Из MDX при сборке извлекаются заголовки, ссылки и текст для оценки времени чтения. Явные английские якоря задаются в разметке заголовков через поддержку синтаксиса `{#anchor}` в обработчике MDX; заголовки остаются частью дерева Markdown. Один набор заголовков используется в HTML, оглавлении и проверках. Смена русского названия раздела не меняет якорь; повторный якорь и неверный формат останавливают сборку (описание — в [обзоре](overview.md#якоря-и-оглавление)).

До подключения журнала дата обновления вычисляется по последнему коммиту файла статьи в Git; дата сборки её не заменяет. Целевой источник видимой даты и сортировки — последнее содержательное дополнение из журнала, а без дополнений — публикация. Новый локальный файл без истории показывается как «Черновик». Для опубликованной сборки отсутствие даты и неполная история считаются ошибкой; CI получает полную историю репозитория. Локальная сборка нового файла до коммита задаётся `ALLOW_DRAFT_ARTICLES=1`; dev-сервер включает режим сам. Автоматическое время чтения — `max(1, ceil(words / 180))`, без frontmatter, кода, математической разметки и служебной разметки компонентов; видимый текст учебных блоков (содержимое и атрибуты `title`, `question`, `caption`) учитывается; ручное `readingMinutes` заменяет оценку; описание — в [обзоре](overview.md#время-чтения).

Логические маршруты и цели ссылок не включают префикс размещения. Общая функция построения URL добавляет базовый путь ровно один раз и сохраняет query и якорь. Она используется для страниц, ресурсов, глоссария, поиска и копирования адреса раздела. Ссылки внутри MDX проходят такое же преобразование при сборке.

Для обычных блоков кода MDX автоматически добавляются шапка языка, подсветка Shiki и копирование полного исходного текста.

### Заметки «Подробнее»

`MarginNote` принимает обязательный `items`: от одной до трёх записей `{ label, description, target }`. Название и пояснение — непустой обычный текст; `target` использует общий контракт `{ article, anchor? }` или `{ url }`. Для раздела автор задаёт `label` в виде «Статья → раздел». Ошибочные поля и количество ссылок останавливают сборку; существование внутренних страниц и якорей проверяется по готовому HTML.

В default-слоте находится ровно один связанный абзац, оформленный Markdown между пустыми строками или элементом `<p>`. Компонент оборачивает его и следующий сразу за ним `<aside aria-label="Подробнее">` в общую строку сетки; ссылка включает название и пояснение. Заметка доступна без JavaScript. Навигационный текст заметок исключён из Pagefind через `data-pagefind-ignore`, основной абзац индексируется.

## Ссылки между материалами

- Статьи содержат перекрёстные ссылки на связанные материалы и объяснения необходимых понятий внутри сайта.
- Если нужного материала на сайте нет, ссылка ведёт на соответствующую статью Википедии.
- Внутренняя ссылка может вести прямо на раздел статьи с нужным понятием.
- Для углубления темы, затронутой в конкретном абзаце, используются заметки «Подробнее» по [макету](design/7-margin-notes.html): 1–3 ссылки с названием материала и кратким пояснением; ссылка на раздел подписывается «Статья → раздел». Заметки добавляются по смыслу, а не к каждому абзацу; на применимость проверяются все текущие статьи сайта.
- В порядке чтения заметка располагается сразу после связанного абзаца и имеет семантику `<aside aria-label="Подробнее">`. На экранах от 1280 px она выводится справа на уровне первой строки абзаца, шириной 208 px и с отступом от текста 48 px; на узких экранах и при печати — блоком на фоне `--color-surface` под абзацем. Соседние заметки при необходимости сдвигаются вниз и не перекрывают друг друга, оглавление или широкие блоки; горизонтальной прокрутки страницы нет. Ссылки доступны клавиатурой и без JavaScript.
- Заметки дополняют ссылки в основном тексте, подсказки терминов, предварительные знания и связанные темы в конце статьи. Их внутренние цели проверяются при сборке и учитывают базовый путь размещения.

## Треки чтения

- Трек — рекомендуемый порядок чтения опубликованных материалов сайта для определённой аудитории. В первый набор входят все пять треков: «Программист», «Звукорежиссёр», «Музыкант», «Диджей» и «Меломан». Основа оформления — [макет](design/10-tracks.html); пример направления для звукорежиссёра — `scratch/tracks.md`. Пример не является обязательной программой курса: отсутствующие на сайте темы не добавляются в трек и не требуют написания новых статей. Пустые этапы не выводятся.
- Элементы трека — статьи целиком или отдельные существующие разделы. Раздел выбирается, когда остальная статья для этой аудитории избыточна. Можно отмечать элемент «по желанию»; основной маршрут должен быть понятен без него. Внешние материалы, черновики и заглушки будущих статей не включаются. Прогресса прохождения, отметок «Прочитано» и сохранения состояния нет.
- Каждый трек имеет постоянный английский slug, название, описание аудитории и цели, упорядоченные этапы с постоянными id, названиями и пояснениями, а также упорядоченные элементы с постоянными id, внутренними целями и признаком необязательности. Названия статей и разделов берутся из материалов; счётчики этапов и элементов вычисляются. Состав и пояснения всех пяти маршрутов готовятся и передаются автору на локальную проверку отдельной задачей до публикации.
- Каталог `/tracks/` показывает все пять карточек с описанием, количеством этапов и элементов и списком этапов; отдельные страницы — `/tracks/<slug>/`. На широком экране каталог имеет две колонки, на смартфоне — одну. На странице трека — хлебные крошки, название и описание, переключатель всех треков, счётчики и легенда, вертикальная ось с номерами этапов, элементы и дата обновления; связанные треки показываются при наличии. На компьютере пояснение этапа слева, элементы сеткой справа; на смартфоне пояснение над элементами, элементы в одну колонку, переключатель прокручивается горизонтально. Раздел подписан с названием статьи, необязательный элемент — пунктирной рамкой и текстом «по желанию». Ограничение макета «3–6 элементов» — ориентир, а не требование заполнения отсутствующими материалами.
- В шапке «Треки» идёт после «Материалов», в мобильном меню — вторым пунктом. На главной сразу после поиска и перед визуализациями размещается «С чего начать» со всеми пятью карточками; сетка адаптируется к их количеству, на смартфоне — одна колонка.
- Под метаданными статьи показывается «В треках» со ссылками на соответствующие этапы, если статья целиком или её раздел входит в трек. Данные вычисляются из треков, вручную в статье не дублируются. Если статья встречается в нескольких этапах, доступны все соответствующие этапы.
- Ссылки из трека передают `?track=<slug>` перед якорем раздела. В статье, открытой из трека, в конце тела статьи перед связанными темами появляется блок с названием трека, номером этапа и элемента, ссылкой «Весь трек» и переходами к предыдущему и следующему элементам в общем порядке, включая элементы «по желанию». Для разделов блок также находится в конце статьи. На краях отсутствующий переход скрывается. Контекст сохраняется в соседних переходах; обычные ссылки статьи его автоматически не переносят. Постоянный id элемента передаётся в query как `item` для однозначного выбора позиции, в том числе когда несколько элементов ведут в одну статью. Без параметра, при неизвестном треке или несовместимом элементе блок не выводится. Переход к разделу выделяет целевой заголовок через `:target` по образцу подсветки термина глоссария.
- Страницы треков, карточки, обратные ссылки статьи и переходы работают с учётом `base`; основной маршрут доступен без JS. Условный блок в статье определяется в браузере по query и без JS скрыт. Навигационные блоки в статьях и карточки на главной исключаются из Pagefind; каталог и страницы треков также исключаются, чтобы поиск сохранял текущий состав статей и глоссария.
- Создание трека отражается записью «Новое», содержательное изменение состава, порядка и пояснений — новой записью «Дополнено». Опечатки и форматирование не записываются. Записи появляются в журнале, архиве, RSS и блоке «Недавно на сайте» на общих условиях. Дата обновления трека — последняя запись «Дополнено», а без неё — «Новое»; в локальном просмотре до публикации показывается «Черновик». Запись готовится вместе с треком и включается в коммит после авторского одобрения.

### Контракт данных трека

Источник — коллекция `tracks`, один JSON-файл `src/content/tracks/<slug>.json` на маршрут. Схема, загрузчик и проверка целей реализованы в задаче 64; реальное наполнение готовится в задаче 69. Устройство и служебные проверки описаны в [обзоре](overview.md#данные-треков-и-проверка-целей).

| Поле | Контракт |
| --- | --- |
| `slug` | Уникальный постоянный английский kebab-case, начинается с буквы; совпадает с именем файла и задаёт `/tracks/<slug>/` |
| `title` | Непустое русское название аудитории: «Программист» и т. п. |
| `audience` | Непустой обычный текст о том, кому подходит маршрут; используется в карточке |
| `description` | Непустой обычный текст о цели и содержании маршрута; используется на странице трека |
| `stages` | Непустой массив этапов `{ id, title, description, items }` в порядке чтения |
| `stages[].id` | Постоянный kebab-case, начинается с буквы, уникален внутри трека; якорь этапа — `stage-<id>` |
| `stages[].title`, `description` | Непустые название и пояснение этапа обычным текстом |
| `stages[].items` | Непустой массив элементов `{ id, target, optional? }` в порядке чтения |
| `items[].id` | Постоянный kebab-case, начинается с буквы, уникален во всём треке, включая разные этапы; передаётся как `item` |
| `items[].target` | Ровно `{ article, anchor? }`: slug опубликованной статьи и необязательный существующий якорь её заголовка H2–H4; внешние цели, термины и рисунки самостоятельными элементами не являются |
| `items[].optional` | Необязательный boolean, по умолчанию `false`; при `true` — «по желанию» |
| `related` | Необязательный массив `{ track, description }`: slug другого существующего трека и непустое пояснение связи; без повторов и ссылки на себя |

Первый набор и порядок во всех списках: `programmer` — «Программист», `sound-engineer` — «Звукорежиссёр», `musician` — «Музыкант», `dj` — «Диджей», `music-lover` — «Меломан». Порядок этапов и элементов задаётся массивами, отдельные числовые позиции не хранятся. При перестановке сохраняются id; номер этапа и позиция элемента вычисляются. Точное наполнение не закрепляется макетом и готовится в задаче 69.

Названия элементов и подписи родительских статей извлекаются из статей и их заголовков. Счётчики включают все элементы, в том числе необязательные; соседние переходы используют плоскую последовательность этапов и их элементов. Обратный список статьи включает и цели без якоря, и её разделы: каждую пару «трек/этап» показывать один раз. Связанные треки не обязаны перечислять друг друга взаимно.

Сборка проверяет формат, непустые поля и массивы, уникальность slug, id и целей внутри трека, существование статей, заголовков и связанных треков. Статья целиком и разные её разделы — разные цели; повтор одинаковой пары `article/anchor` запрещён. Пустые этапы при подготовке маршрута удаляются, а в исходниках считаются ошибкой; рендер не создаёт для них заглушек. Для публикации статья должна уже иметь запись «Новое» в журнале, а трек — собственную запись «Новое». Локальный просмотр и служебные тестовые наборы могут проверяться до появления записи трека; публичная сборка не включает служебные маршруты. Произвольные HTML/Markdown и неизвестные поля в данных трека не допускаются. Формат JSON, схема и связи проверяются при сборке; публикация и даты самого трека проверяются и вычисляются из журнала.

### Контекст и адреса

- Ссылка элемента всегда передаёт `track` и `item`: `/<article>/?track=<slug>&item=<id>#<anchor>` (без hash для целой статьи). `item` — id элемента, а не номер; параметры находятся перед якорем. Логические адреса не содержат `base`, построитель добавляет его ровно один раз.
- Если передан `item`, он должен существовать в указанном треке и вести в текущую статью; для цели-раздела hash должен совпадать с её якорем. Неизвестный или несовместимый id скрывает блок, без подмены другим элементом. Если `item` отсутствует, позиция определяется только по единственному совпадению `article/anchor`; отсутствие или неоднозначность совпадения скрывает блок. Повторные параметры `track`/`item` считаются неверным контекстом. Изменение hash и переходы истории браузера повторно определяют контекст.
- «Весь трек» ведёт на `/tracks/<slug>/#stage-<id>` текущего этапа. Соседние ссылки сохраняют `track` и передают собственный `item` и якорь; переход может вести в другой раздел той же статьи. Номер элемента — позиция во всём маршруте, номер этапа — позиция этапа.
- «В треках» ведёт на якоря этапов без контекста статьи. Ссылки каталога, главной, переключателя и связанных треков ведут на страницы треков. Неизвестный slug страницы трека даёт 404. Контекст чтения не хранится в storage и не переносится на обычные ссылки статьи.

## Журнал обновлений и RSS

### Записи и даты

- Журнал добавляется вручную при публикации новой статьи или трека либо их существенном дополнении; исправления опечаток, форматирование и технические изменения сайта не записываются. «Новое» — новая статья с её визуализациями и терминами; «Дополнено» — новый раздел, визуализация, пример, вопросы самопроверки или исправление по существу в опубликованной статье. Каждая запись относится к одной статье или одному треку. Для трека «Новое» означает создание маршрута, «Дополнено» — содержательное изменение состава, порядка или пояснений. Самостоятельных записей о глоссарии нет: новые термины перечисляются в записи соответствующей статьи.
- Источник — коллекция `updates`. Запись содержит неизменяемый уникальный `id` (английские строчные буквы, цифры и дефисы, начинается с буквы), `date` (существующая календарная дата `YYYY-MM-DD`), `order` (положительное целое число, уникальное в пределах дня), `type` (`new` — «Новое», `updated` — «Дополнено»), ровно одну цель материала — `article` (slug статьи) или `track` (slug трека) — и `items` (0–4 пункта для `new`, 1–4 для `updated`). Для `new` обязателен `summary` — непустое краткое описание содержания материала обычным текстом, подготовленное автором и используемое в журнале и RSS; для `updated` поле не требуется. Пункт — `{ text, target }`: непустой текст целиком является ссылкой. Произвольные HTML и Markdown в тексте не допускаются.
- Название записи — актуальное название статьи или трека; для трека строка метаданных — «Трек · <число этапов> · <число элементов>», вычисляемая из его данных; строка метаданных «Статья · <группа> · <время чтения>» берётся из статьи. Название, группа и время чтения не дублируются в записи. Цель пункта — внутренняя статья или её раздел/рисунок/визуализация `{ article, anchor? }`, либо термин `{ glossary: id }`, либо трек или его этап `{ track, anchor? }`. Внешние адреса не допускаются; глоссарная цель дополняет общий контракт внутренних целей и разрешается в `/glossary/#<id>`. Цель `{ track, anchor? }` использует slug трека и, при наличии, полный якорь `stage-<id>` его этапа. Slug статей и треков, якоря и термины проверяются при сборке. Варианты `article`, `glossary`, `track` взаимоисключающие; расширение внутренних целей журнала не разрешает внешние ссылки в нём или ссылки на треки как элементы маршрута.
- `date` — день публикации изменения по московскому времени (`Europe/Moscow`), указывается автором и не вычисляется из времени сборки или последнего коммита. Будущие даты запрещены. Для уже опубликованных записей `id` и `date` сохраняются при последующих дополнениях и правках текста. Для одного материала допускается несколько записей одного дня, у каждой собственный `id`.
- У статьи или трека не более одной записи «Новое»; для публикации трека такая запись обязательна. Идентичные slug статьи и трека не конфликтуют: идентичность материала — пара «вид/slug». «Дополнено» не может предшествовать дате публикации материала. При первоначальном заполнении у каждой текущей статьи создаётся «Новое» с датой первого коммита её файла (с учётом переименований, календарный день по `Europe/Moscow`); прошлые дополнения не восстанавливаются. Запись «Новое», в том числе историческая, может не содержать пунктов; достаточно названия-ссылки и краткого описания содержания. При необходимости добавляются до четырёх пунктов; для «Дополнено» обязательны 1–4 пункта изменений. До заполнения журнала для проверок используются служебные записи, не попадающие на публичный сайт и в RSS.
- Под заголовком статьи нет отдельной Git-даты «Обновлено»; выводятся только «Опубликовано» и «Дополнено». Карточки, список материалов и тематические группы главной используют дату последнего содержательного дополнения из журнала, а без дополнений — публикацию; Git-коммиты с опечатками не меняют порядок. «Опубликовано <дата>» берётся из записи «Новое»; для будущих статей день публикации указывается вручную, для существующих при начальном заполнении журнала — день первого коммита файла с учётом переименований; до появления записи — дата первого коммита файла, для нового файла без истории — «Черновик». «Дополнено <дата>» берётся из последней записи `updated` этой статьи и ведёт на неё в журнале; без дополнений эта метка отсутствует. Дата публикации и дата дополнения могут различаться; Git-дата не выводится под заголовком статьи.

### Страница, архив и ссылки

- `/updates/` — страница «Обновления»: заголовок, вводный абзац «Новые материалы и дополнения к опубликованным, по датам. Ссылки ведут прямо к изменённому месту.», фильтр «Все · Новое · Дополнено», ссылка «RSS-лента», секции дат и архив «Ранее:». Даты идут по убыванию; записи одной даты — по `order` по убыванию. Порядок задаётся вручную: более поздняя публикация получает большее число и показывается выше; при одновременной публикации порядок выбирает автор. Тот же порядок применяется на главной и в RSS; последняя запись статьи при равных датах — первая в этом порядке. Изменение `order` не меняет идентификатор или дату записи.
- Текущий год журнала — максимальный год среди опубликованных записей, а не календарный год сборки или браузера. Он указан под заголовком страницы. Если записей нет, показывается «Обновлений пока нет» без года и архива. Страница показывает весь выбранный год, без пагинации.
- Для каждого года с записями, включая текущий, создаётся постоянный адрес `/updates/YYYY/`; его заголовок — «Обновления за YYYY год». `/updates/` показывает тот же набор, что страница последнего года. Несуществующий или пустой год даёт 404. «Ранее:» содержит непустые годы старше выбранного по убыванию, а страница архива также содержит ссылку «Последние обновления» на `/updates/`.
- Каждая дата — `<h2 id="YYYY-MM-DD">` с `<time datetime="YYYY-MM-DD">`. Каждая запись имеет дополнительный постоянный якорь `update-<id>`. Ссылка на дату — `/updates/YYYY/#YYYY-MM-DD`, на конкретную запись — `/updates/YYYY/#update-<id>`. Эти адреса используются с главной, из статьи и RSS и не меняются при наступлении нового года. Прямые якоря работают и на `/updates/` для отображаемого года.
- С JS фильтр хранится в `?type=new` или `?type=updated`; для «Все» параметр отсутствует. Неизвестное/пустое значение считается «Все» и удаляется при следующем изменении фильтра. Изменение фильтра создаёт запись истории, «Назад» и «Вперёд» восстанавливают выбор. Остальные параметры и якорь сохраняются. Пустые секции дат скрываются; при отсутствии совпадений — «Нет обновлений этого типа за <год>». Если прямой якорь указывает на запись или день, скрытый фильтром, выбирается «Все» с заменой текущей записи истории, затем выполняется переход к якорю.
- Без JS весь выбранный год виден независимо от query; фильтр показывается только после подключения JS. Архив и ссылки работают без JS. При переходе между годами фильтр сбрасывается в «Все».
- Главная после визуализаций и до тематических групп показывает «Недавно на сайте»: три последние записи из всего журнала (или все, если меньше трёх), дата, метка типа и текст-ссылка на конкретную запись. Текст — название статьи или трека; для «Дополнено» к нему через двоеточие добавляется текст первого пункта. «Все обновления» ведёт на `/updates/`; пустой блок не выводится.
- В подвале всех страниц добавляются «Обновления» (`/updates/`) и «RSS» (`/updates/feed.xml`); остальные ссылки сохраняются. Пункт «Треки» в шапке добавляется по требованиям треков. Внутренние адреса учитывают фактический `base` ровно один раз.
- Страницы журнала и архива целиком исключаются из Pagefind; RSS также не индексируется. Блок «Недавно на сайте» и ссылки на журнал в метаданных статьи исключаются через `data-pagefind-ignore`, чтобы не дублировать текст статей в поисковой выдаче.

### RSS

- Статическая RSS 2.0-лента `/updates/feed.xml` строится из всех опубликованных записей всех лет, без фильтра и ограничения количества: одна запись — один `item`. Полный текст статьи в ленту не включается.
- Канал: `title` — «Теория аудио — обновления», `link` — абсолютный адрес `/updates/`, `description` — вводный абзац журнала, `language` — `ru`. Пустой журнал даёт валидный канал без элементов.
- Новые статьи и треки также публикуются в RSS при выходе. Элемент `new`: `title` — «Новое: <название материала>», `link` — абсолютный адрес статьи или трека, `description` — краткое описание содержания из `summary` и ссылка «Читать статью» или «Открыть трек» в зависимости от вида материала. Элемент `updated`: `title` — «Дополнено: <название материала>», `link` — абсолютный постоянный адрес записи в архиве, `description` — ссылка на статью или трек и HTML-список всех пунктов изменений с их ссылками. Полный текст статьи не включается; содержимое `description` экранируется для XML. `guid` — `audio-theory-update:<id>` с `isPermaLink="false"`, не зависит от названия, slug, домена, базового пути или текста пунктов. `pubDate` — дата записи в 00:00:00 московского времени, сериализованная в формат RSS с четырёхзначным годом и часовым поясом `+0300`; дата сборки её не заменяет. Обновление статьи или трека создаёт новый элемент с новым `id`, прежние `guid` и `pubDate` не меняются.
- Все адреса внутри XML абсолютные: публичный origin из конфигурации сайта плюс фактический базовый путь. Ресурс входит в артефакт GitHub Pages. В `<head>` всех HTML-страниц добавляется `<link rel="alternate" type="application/rss+xml" title="Теория аудио — обновления">` с адресом ленты.
- Формат XML, `guid`, `description` и `pubDate` следуют [спецификации RSS 2.0](https://www.rssboard.org/rss-specification). Проверка реализации: валидатор RSS, чтение RSS-ридером, неизменность старых идентификаторов и дат при добавлении записей, сборки в корне и под префиксом и загрузка публичной ленты после деплоя.
- Журнал, годовой архив, RSS, ссылки с главной, статей и подвала, запись при подготовке материала и начальное заполнение по истории текущих статей входят в первый выпуск (задачи 57–62); поддержка треков добавляется на этапе 10 (задачи 63–69).

## Поиск

- Полнотекстовый поиск по текстам статей, включая английские названия понятий и терминов.
- Поисковый движок — Pagefind. Индекс создаётся из готовых HTML-страниц при каждой сборке и публикуется вместе с сайтом.
- До полной реализации поискового попапа проверяется поиск по первым статьям: русский текст и словоформы, английские термины на русскоязычных страницах и переходы к разделам.
- Поиск открывается в попапе с полем запроса и результатами.
- Глобальный поиск по страницам сайта открывается с любой страницы горячей клавишей `/`; фокус сразу переходит в поле поискового запроса. При вводе текста в поле ввода или редактируемой области эта горячая клавиша не срабатывает.
- Стрелки `↑` и `↓` перемещают выделение по результатам поиска; выбранный результат визуально выделяется. Клавиша `Enter` открывает выбранный результат.
- Поиск работает в браузере без серверной части и совместим со статическим размещением на GitHub Pages.

## Поддерживаемые браузеры

- Поддерживаются актуальные стабильные Chrome и Firefox на компьютерах, Safari на macOS и iOS, Chrome на Android.
- Приоритетные браузеры для автора — Safari на macOS и iOS. Основные сценарии чтения, поиска, навигации, переключения темы и интерактивного примера со звуком проверяются в них в первую очередь.

## Работа агента

- В репозитории доступны скиллы `commit`, `execute`, `issue` и `write-article` в вариантах для Codex (`.agents/skills/`) и Claude Code (`.claude/skills/`). `commit` проверяет и коммитит изменения, `execute` выполняет указанный пункт `docs/todos.md`, `issue` доводит GitHub issue до проверенного результата и отчёта. `write-article` готовит или дополняет материал по теме и уточнениям до авторской проверки; самостоятельно не коммитит и не публикует. `execute` и `issue` вызывают его при подготовке материалов и сохраняют ответственность за завершение задачи. Правила авторской проверки и публикации материалов сохраняются во всех процессах; вызовы описаны в [README](../README.md#скиллы-агентов).
- При реализации изменений команд, путей, проверок и процесса подготовки или публикации материалов затронутые скиллы обновляются в обоих вариантах вместе с реализацией. Соответствующие действия и критерии проверки включены в [задачи](todos.md).
- Результаты проверки материалов агент кратко сообщает автору в ответе; отдельные документы с отчётом о проверках не создаёт.
- Скилл для Codex и Claude Code запускает создание или дополнение материалов на указанную пользователем тему.
- Скиллы Codex и Claude Code используют один общий набор правил подготовки статей, хранящийся в репозитории. Правила не дублируются для каждого агента; общие [правила](authoring/rules.md), [чеклист](authoring/checklist.md) и [шаблон](authoring/article-template.mdx) находятся в `docs/authoring/`; пути описаны в [structure.md](structure.md), подключение и проверка — в [плане реализации](plan.md#4-подготовить-общий-скилл-и-первые-тексты).
- Рекомендуемые источники для подготовки материалов хранятся в пополняемом [списке](authoring/sources.md). Хорошие источники, найденные и изученные при работе, добавляются туда с указанием подходящих тем. Первый рекомендованный автором источник — Steven W. Smith, *The Scientist and Engineer's Guide to Digital Signal Processing*. Для утверждений статьи всё равно проверяется конкретный раздел источника.
- Перед написанием агент изучает существующие статьи и связанные темы.
- Если запрошенную тему лучше раскрыть внутри существующей статьи, агент дополняет эту статью.
- Новая статья создаётся, когда теме подходит самостоятельное изложение.
- Если тема уже раскрыта, агент дорабатывает материал только там, где это необходимо, избегая дублирования.
- При подготовке материала агент соблюдает требования к языку и уровню объяснений и учитывает уточнения пользователя.
- При использовании нового математического инструмента в статье агент в том же изменении расширяет `/audio-math/`: объяснение с основ, числовой пример, условия применения и источник. Если инструмент уже объяснён, материал ссылается на соответствующий раздел. Обе версии `write-article` используют это правило из [общих правил](authoring/rules.md#выбор-материала); дополнения проходят авторскую проверку вместе с основным материалом.
- После написания или дополнения текста агент проверяет его по [каталогу избитых LLM-тропов tropes.md](https://tropes.fyi/tropes-md), а если сайт недоступен — по локальной копии `docs/authoring/tropes.md`, и исправляет найденные шаблонные обороты, повторы и другие перечисленные в каталоге приёмы. Проверка учитывает их русскоязычные аналоги; правки должны сохранять техническую точность и понятность объяснений. Агент завершает эту проверку до передачи материала пользователю на личную проверку.

## Проверка и публикация

- Автоматический деплой на GitHub Pages настраивается в начале разработки, чтобы проверять готовые части сайта на реальном публичном адресе. Публикация технического каркаса не требует готовности полного первого выпуска; статьи и изменения материалов публикуются только после авторской проверки.
- Агент готовит новую статью или изменения существующей локально; пользователь читает материал на локально запущенном сайте.
- Пользователь задаёт уточняющие вопросы и просит доработки. Агент дорабатывает материал, пока объяснения не станут понятны пользователю и статья не будет его устраивать.
- После одобрения пользователем выполняются коммит и пуш в основную ветку. PR для этого процесса не требуется; непроверенные изменения материалов не включаются в публикуемый коммит.
- Пуш в основную ветку запускает автоматическую сборку и деплой на GitHub Pages. Один процесс применяется к новым статьям и доработкам опубликованных материалов.
- В CI запускается минимальный обязательный набор E2E: не более 12 проверок (11 сценариев `@ci` в WebKit под префиксом GitHub Pages и один `@ci-root` в Chromium в корне), прогон не дольше 3 минут. Жёсткое правило: набор не растёт — новым сценариям метка `@ci` не ставится, лимит не повышается, а новый сценарий CI заменяет существующий; CI проверяет лимит до сборок (`scripts/check-e2e-budget.mjs`). Полная матрица всех сценариев доступна отдельно для диагностики; распределение описано в [обзоре](overview.md#браузерные-проверки).
- Перед деплоем в CI обязательны проверка линтером, проверка типов, тесты, сборка сайта и поискового индекса, проверка метаданных, внутренних ссылок и якорей, а также основные браузерные сценарии. Ошибка любой обязательной проверки останавливает деплой.
- Соответствие макетам и работа в настоящем Safari на Mac и iPhone проверяются вручную до публикации, включая интерактивный пример и звук. Личная проверка контента остаётся обязательной частью процесса.
