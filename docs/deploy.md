# CI и GitHub Pages

Основная ветка репозитория `hazadus/audio-theory` — `main`. GitHub Pages включён с источником **GitHub Actions** (`build_type: workflow`, HTTPS включён). Целевой публичный адрес — https://hazadus.github.io/audio-theory/. Первый деплой ожидает проверки подготовленного workflow, коммита и пуша; до его успешного завершения публичный сайт не считается проверенным.

Workflow [`.github/workflows/pages.yml`](../.github/workflows/pages.yml) называется **GitHub Pages**. Он запускается при пуше в `main`, для pull request в `main` и вручную через Actions. PR проверяется без публикации; ручной запуск публикует только `main`. Публикация обычной задачи не требует PR.

Runner — Ubuntu 24.04, Node.js — 22.23.1. Официальные Actions закреплены SHA с комментариями о версиях; npm-зависимости устанавливаются через `npm ci` по `package-lock.json`. Checkout получает полную историю (`fetch-depth: 0`) для будущих Git-дат статей. Кеш npm ускоряет загрузку пакетов и не заменяет установку по lock-файлу.

CI выполняет `npm run fmt:check`, `lint`, `typecheck`, `test`, `test:mdx` и полный `test:e2e`, устанавливая Chromium, Firefox и WebKit с системными библиотеками. Это те же npm-команды, что вызывают локальные рецепты `just`; установка `just` в CI не нужна. Проверка MDX включает ошибочную формулу и отсутствие тестовых материалов в обычной сборке; unit-тесты подтверждают, что ошибочная внутренняя ссылка блокирует сборку.

`test:e2e` строит HTML и Pagefind в `.e2e/root/` и `.e2e/prefixed/`, проверяет локальные страницы, якоря и ресурсы, затем запускает браузерные сценарии и настоящий поиск. После успеха всех проверок `upload-pages-artifact` загружает **именно `.e2e/prefixed/`**, проверенный браузерами под `/audio-theory/`. Деплой получает этот артефакт того же запуска, без новой сборки. Локальный `just build` по-прежнему создаёт `dist/`. В CI сейчас проверяется готовый каркас; проверки метаданных и нумерации будут подключены вместе с коллекцией статей.

У всего workflow только `contents: read`; дополнительные `pages: write` и `id-token: write` выдаются заданию `deploy`, которое зависит от успешного `build` и использует окружение `github-pages`. Ошибка любого обязательного шага блокирует загрузку артефакта и деплой: `continue-on-error` и обхода через `always()` нет. Группа concurrency `pages-${{ github.ref }}` с `cancel-in-progress: false` не допускает одновременных публикаций из `main` и даёт текущему деплою завершиться; PR проверяются независимо.

## Настройка Pages в новом репозитории

В **Settings → Pages → Build and deployment → Source** выбрать **GitHub Actions**. Для существующего репозитория это уже сделано. Эквивалент создания сайта через GitHub CLI:

```sh
gh api --method POST repos/hazadus/audio-theory/pages -f build_type=workflow
```

Если сайт уже существует с другим источником, использовать `--method PUT`. Проверить настройку:

```sh
gh api repos/hazadus/audio-theory/pages --jq '{build_type, html_url, https_enforced}'
```

Окружение `github-pages` должно разрешать деплой из `main`; если в нём настроено ручное одобрение, дождаться его. Персональный токен в workflow не нужен. Правила и необходимые права описаны в [официальной документации GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Проверка публикации нужного коммита

Проверки, которые требуют нового коммита на GitHub (CI, деплой и публичный сайт), выполняются после разрешённого технического коммита и пуша. Их ожидание не запрещает необходимый для запуска проверок коммит: сначала завершить все доступные локальные проверки, затем выполнить порученную публикацию, не отмечая задачу выполненной до успешных CI, деплоя и публичной проверки. Явная просьба пользователя отложить коммит имеет приоритет.

Коммит и пуш — отдельные действия. Перед коммитом проверить состав изменений; неодобренные статьи, определения глоссария и текст «О проекте» оставить вне публикуемого коммита. Технический каркас можно публиковать до готовности материалов. Если пользователь попросил сначала проверить изменения, дождаться его ответа до коммита и пуша. Скилл `commit` сам не публикует сайт; пуш допустим по явной просьбе либо по прямому требованию выбранного пункта плана.

После разрешённого коммита и при порученной публикации:

```sh
TASK_DEPLOY_SHA=$(git rev-parse HEAD)
git push origin main
gh run list --repo hazadus/audio-theory --workflow pages.yml --branch main --commit "$TASK_DEPLOY_SHA" --event push --limit 10 --json databaseId,headSha,status,conclusion,url
```

Если запуск ещё не появился, повторить получение списка. Сохранить `databaseId` запуска нужного SHA как `TASK_RUN_ID`; не выбирать просто последний workflow репозитория:

```sh
TASK_RUN_ID=123456789 # Заменить на databaseId найденного запуска.
gh run watch "$TASK_RUN_ID" --repo hazadus/audio-theory --exit-status --interval 10
gh run view "$TASK_RUN_ID" --repo hazadus/audio-theory --json headSha,headBranch,event,conclusion,jobs,url
```

Убедиться, что `headSha` совпадает с `TASK_DEPLOY_SHA`, ветка — `main`, итог — `success`, а задание **Деплой GitHub Pages** и шаг **Опубликовать проверенный артефакт** завершились с `success`, не `skipped`. Успех только задания сборки ещё не означает публикацию. При ошибке прочитать `gh run view "$TASK_RUN_ID" --repo hazadus/audio-theory --log-failed`, исправить причину и проверить новый запуск по его SHA.

Открыть URL окружения `github-pages` из этого запуска: https://hazadus.github.io/audio-theory/. Проверить заголовок «Теория аудио», отображение страницы, переход на главную, `/audio-theory/licenses/katex.txt` и загрузку `/audio-theory/pagefind/pagefind.js`; запрос API Pagefind из [README](../README.md#поисковый-индекс-и-проверка-артефакта) должен найти начальную страницу. `just test-production` появится в следующей задаче и сейчас не считается выполненным.

Для завершения первой настройки требуется также контрольная ошибка обязательной проверки в CI: неуспешный `build` должен оставить загрузку Pages-артефакта и зависимый `deploy` невыполненными. Ошибочную правку не публиковать как готовый каркас; после её удаления проверить успешный запуск исправленного SHA. До первого пуша эта CI-проверка, успешный деплой и доступность публичной страницы остаются открытыми.

В итоговом отчёте о публикации указать проверенный полный SHA, ссылку на запуск workflow, публичный адрес и результаты проверок. Если коммит или пуш отложен пользователем либо обязательная проверка недоступна, не отмечать пункт выполненным и назвать оставшиеся проверки.
