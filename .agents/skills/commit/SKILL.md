# Коммит изменений

Закоммитить текущие staged, unstaged и untracked изменения по [стайлгайду](../../../docs/styleguide.md) с учётом [правил проверки и публикации](../../../docs/spec.md#проверка-и-публикация).

## Шаги

1. **Осмотреть изменения**
   - Проверить `git status`, `git diff`, `git diff --staged` и содержимое новых файлов. Выяснить, какие изменения связаны между собой и какие проверки для них нужны.

2. **Проверить затронутое**
   - Сборка сайта уже доступна: `just build` вызывает `npm run build` и создаёт статические файлы в `dist/`. Выполнять её при изменениях приложения или конфигурации сборки. Сейчас доступны `just`, `just dev`, `just build`; остальные рецепты проверок добавляются в следующих пунктах и пока не считаются пройденными.
   - Для кода использовать существующие рецепты корневого `justfile`: `just fmt`, `just lint`, `just typecheck`, `just test`, `just build` по характеру изменений. Если рецепт ещё не создан, выполнить доступную прямую команду; отсутствие команды не выдавать за успешную проверку.
   - Для затронутого критичного пользовательского пути выполнить полный `just test-e2e`, когда сценарии и рецепт уже созданы. При изменении поведения сначала обновить относящиеся к нему тесты. Для интерфейса выполнить требуемую задачей браузерную или визуальную проверку.
   - Документация и инструкции без изменения кода не требуют сборки и тестов приложения. Проверить ссылки, актуальность описанного поведения и согласованность со [спецификацией](../../../docs/spec.md). Статьи MDX и определения глоссария требуют проверки контента и сборки.
   - Для материалов изучить существующие статьи и [темы](../../../docs/topics.md), избегать дублирования и соблюдать контракты метаданных, ссылок и учебных компонентов из спецификации. Материалы — на русском с английским названием основного термина при первом упоминании. Проверить источники, термины, формулы и расчёты; выполнить редакционную проверку по tropes.md до передачи автору. Использовать общий набор правил `docs/authoring/`, когда они созданы; до этого руководствоваться спецификацией.
   - Новые статьи до коммита собирать в локальном режиме с состоянием «Черновик»; опубликованная сборка требует настоящей Git-даты. Проверить метаданные, внутренние ссылки и якоря; требования к Git-датам в CI не обходить.
   - При падении применимой проверки исправить причину и повторить её. Если обязательная проверка невозможна, сообщить о препятствии и не коммитить непроверенную работу.

3. **Подготовить коммиты**
   - Статьи, изменения их текста, определения глоссария и текст «О проекте» включать только после локальной проверки и явного одобрения автором. Вызов скилла не заменяет авторскую проверку; уже полученное одобрение текущих правок действует. Неодобренные материалы оставить вне коммита; независимые проверенные изменения можно закоммитить.
   - Разделить несвязанные правки на отдельные логические коммиты. Проверить, что новая переменная окружения описана в `.env.example`, а связанные документы и `README.md` обновлены, если этого требуют правила проекта.
   - Сообщение составить по разделу «Git: сообщения коммитов» [стайлгайда](../../../docs/styleguide.md): русский текст, разрешённый тип, необязательный `scope`, тема не длиннее 72 символов, без точки и трейлеров об инструментах. Номер пункта `docs/todos.md` в сообщение не добавлять.
   - Добавлять конкретные пути через `git add <путь>`. Не включать секреты, локальные `.env`, зависимости, тестовые данные и артефакты сборки.

4. **Закоммитить и проверить**
   - Создать новый коммит без `--no-verify` и без изменения предыдущего коммита. Проверить состав и сообщение через `git log -1 --stat`, затем состояние рабочего дерева.

Не пушить без явной просьбы пользователя или требования выбранной задачи.

Использование: `$commit`
